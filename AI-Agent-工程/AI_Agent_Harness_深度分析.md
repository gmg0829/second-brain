# 研究报告：AI Agent 框架——LLM 周围的基础设施如何决定实际性能

## 摘要

Agent 框架——包裹在 LLM 周围的完整软件基础设施——是区分演示版和生产级 AI Agent 的真正关键。研究表明，仅改变框架（相同的模型、相同的权重）就能让 LangChain 从前 30 名之外跃升至 TerminalBench 2.0 的第 5 名，证明用户所交互的"Agent"实际上是框架产生的 emergent behavior（涌现行为），而非模型本身。本文深入分析了 Anthropic、OpenAI、LangChain 以及更广泛的实践者社区的框架架构，涵盖 12 个不同组件、执行循环、设计权衡，以及模型与其脚手架之间的协同进化原则。

---

## 1. 核心概念：什么是 Agent 框架？

### 1.1 标准公式

> **"如果你不是模型，那你就是框架。"** — Vivek Trivedy，LangChain

"Agent 框架"（agent harness）一词在 2026 年初被正式提出，但这个概念在命名之前就已存在。框架是包裹在 LLM 周围的完整软件基础设施：包括编排循环、工具、记忆、上下文管理、状态持久化、错误处理和护栏。Anthropic 的 Claude Code 文档明确指出："SDK 是驱动 Claude Code 的 Agent 框架。"OpenAI 的 Codex 团队也采用相同的表述，将"Agent"和"框架"等同为非模型基础设施。

### 1.2 类比：LLM 如同一台没有内存的 CPU

Beren Millidge 在 2023 年提供了一个精确的类比：**原始 LLM 是一台没有 RAM、没有磁盘、没有 I/O 的 CPU**。框架提供了缺失的基础设施：

| 组件 | LLM 等价物 |
|------|-----------|
| RAM（快速但有限） | 上下文窗口 |
| 磁盘存储（大量但缓慢） | 外部数据库 |
| 设备驱动程序 | 工具集成 |
| 操作系统 | **框架** |

正如 Millidge 所写：*"我们重新发明了冯·诺依曼架构"*——因为这是任何计算系统的自然抽象。

### 1.3 关键区别

- **"Agent"** = 涌现行为：用户交互的目标导向、使用工具、自我修正的实体
- **"框架"** = 产生该行为的机制

当有人说"我构建了一个 Agent"，他们的意思是构建了一个框架并将其指向一个模型。这个区别至关重要，因为大多数实际性能差异源于框架——而非模型。

### 1.4 证据：框架 > 模型

- **LangChain 的 TerminalBench 跃升**：仅改变包裹其 LLM 的基础设施（相同的模型、相同的权重），就让他们从 30 名之外跃升至 **TerminalBench 2.0 的第 5 名**。
- **自动化优化研究**：另一个项目让 LLM 优化基础设施本身，取得了 **76.4% 的通过率**，超越了手工设计的系统。
- **两个产品、相同模型、不同性能**：TerminalBench 证据明确——仅改变框架就能让 Agent 移动 20+ 个排名位置。

## 2. 三个同心圆工程层级

文章确定了围绕模型的三个嵌套层级：

1. **Prompt 工程** — 制作模型接收的指令
2. **Context 工程** — 管理模型何时看到什么
3. **Harness 工程** — 包含以上两者，加上整个应用基础设施：工具编排、状态持久化、错误恢复、验证循环、安全执行和生命周期管理

框架不是提示词的包装器。它是使自主 Agent 行为成为可能的完整系统。

## 3. 生产级 Agent 框架的十二个组件

### 3.1 编排循环（心跳）

实现 **Thought-Action-Observation (TAO) 循环**，也称为 **ReAct 循环**。循环运行：组装提示词 → 调用 LLM → 解析输出 → 执行工具调用 → 反馈结果 → 重复直到完成。

- 从机械角度讲，它通常只是一个 `while` 循环
- 复杂性在于循环所管理的一切，而非循环本身
- Anthropic 将其运行时描述为 **"笨循环"**——所有智能都在模型中；框架只管理轮次

### 3.2 工具层（Agent 的双手）

工具定义为模式（名称、描述、参数类型），注入到 LLM 上下文中以便模型知道可用的内容。工具层处理：

- 注册
- 模式验证
- 参数提取
- 沙箱执行
- 结果捕获
- 将结果格式化为 LLM 可读的观察

**Claude Code** 提供六个类别的工具：文件操作、搜索、执行、网页访问、代码智能和子 Agent 派生。

**OpenAI 的 Agents SDK** 支持：
- 函数工具（通过 `type: "function"`）
- 托管工具（WebSearch、CodeInterpreter、FileSearch）
- MCP 服务器工具

### 3.3 记忆系统（多时间尺度持久化）

记忆在多个时间尺度上运作：

- **短期记忆**：单个会话内的对话历史
- **长期记忆**：跨会话持久化

**实现方法：**
- Anthropic：项目文件和自动生成的 `memory/` 文件
- LangGraph：命名空间组织的 JSON Stores
- OpenAI：SQLite 或 Redis 支持的会话

**Claude Code 的三层层次结构：**
1. **轻量级索引**（每个条目约 150 字符，始终加载）
2. **详细主题文件**（按需加载）
3. **原始转录**（仅通过搜索访问）

**关键设计原则**：Agent 将自己的记忆视为"提示"，在行动前根据实际状态进行验证。

### 3.4 上下文管理（许多 Agent 在这里悄然失败）

核心问题是 **上下文腐烂**：当关键内容落在窗口中间位置时，模型性能下降 **30%+**（Chroma 研究证实，与斯坦福的"Lost in the Middle"发现一致）。即使是百万 token 窗口，随着上下文增长，指令遵循能力也会退化。

**五种生产策略：**

| 策略 | 描述 |
|------|------|
| **压缩** | 当接近限制时总结对话历史（Claude Code 保留架构决策和未解决的 bug，同时丢弃冗余的工具输出） |
| **观察掩码** | JetBrains 的 Junie 隐藏旧工具输出，同时保持工具调用可见 |
| **即时检索** | 维护轻量级标识符并动态加载数据（Claude Code 使用 grep、glob、head、tail，而非加载完整文件） |
| **子 Agent 委托** | 每个子 Agent 广泛探索，但只返回 1,000 到 2,000 token 的浓缩摘要 |

**ACON 研究**：通过优先考虑推理痕迹而非原始工具输出，在保持 95%+ 准确率的同时减少 **26 到 54%** 的 token。

**Anthropic 的指导原则**：*"找到最小的高信号 token 集合，以最大化预期结果的概率。"*

### 3.5 提示词组装

组装模型在每一步实际看到的内容。**层级结构：**
1. 系统提示词
2. 工具定义
3. 记忆文件
4. 对话历史
5. 当前用户消息

**OpenAI Codex 的优先级堆栈：**
1. 服务器控制的系统消息（最高优先级）
2. 工具定义
3. 开发者指令
4. 用户指令（级联的 `CLAUDE.md` 文件，32 KiB 限制）
5. 对话历史

### 3.6 工具调用与输出分类

现代框架依赖 **原生工具调用**，模型返回结构化的 `tool_calls` 对象，而非需要解析的自由文本。框架检查：有工具调用吗？执行并循环。没有工具调用？那就是最终答案。

**对于结构化输出：**
- OpenAI 和 LangChain 都通过 Pydantic 模型支持模式约束响应
- 传统方法如 `RetryWithErrorOutputParser`（将原始提示词 + 失败补全 + 解析错误反馈给模型）仍可用于边缘情况

### 3.7 状态管理与检查点

**LangGraph** 将状态建模为流经图形节点的类型化字典，使用 reducer 合并更新。检查点发生在超步边界，支持：
- 中断后恢复
- 时间旅行调试

**OpenAI** 提供四种互斥策略：
1. 应用内存
2. SDK 会话
3. 服务器端 Conversations API
4. 轻量级 `previous_response_id` 链接

**Claude Code** 采用不同方法：
- Git 提交作为检查点
- 进度文件作为结构化草稿

**为什么这很重要**：一个 10 步过程，每步 99% 成功率，仍然只有 **~90.4%** 的端到端成功率。错误快速累积。

### 3.8 错误处理

**LangGraph 区分四种错误类型：**

| 错误类型 | 策略 |
|---------|------|
| **瞬态** | 指数退避重试 |
| **LLM 可恢复** | 将错误作为 `ToolMessage` 返回，以便模型调整 |
| **用户可修复** | 中断等待人工输入 |
| **意外** | 冒泡供调试 |

**Anthropic 的方法**：在工具处理器中捕获失败，并返回错误结果以保持循环运行。

**Stripe 的生产框架**：将重试次数上限设为 **两次**。

### 3.9 护栏与安全架构

**OpenAI 的三级实现：**
1. **输入护栏**（在第一个 Agent 上运行）
2. **输出护栏**（在最终输出上运行）
3. **工具护栏**（在每次工具调用上运行）

**"断路器"机制** 在触发时立即停止 Agent。

**Anthropic 的架构分离：**
- 模型决定尝试什么
- 工具系统决定允许什么

Claude Code 独立控制 **~40 个离散工具能力**，分为三个阶段：
1. 项目加载时建立信任
2. 每次工具调用前检查权限
3. 高风险操作需要用户明确确认

### 3.10 验证循环

这是区分玩具演示和生产级 Agent 的关键。**三种方法：**

| 方法 | 技术 |
|------|------|
| **基于规则反馈** | 测试、linter、类型检查器 |
| **视觉反馈** | 通过 Playwright 进行 UI 任务截图 |
| **LLM 作为裁判** | 单独的子 Agent 评估输出 |

**关键发现**：Boris Cherny（Claude Code 创造者）指出，让模型有能力验证自己的工作可以将质量提高 **2 到 3 倍**。

### 3.11 多 Agent 编排

**Claude Code 的三种执行模型：**
- **Fork**：父上下文的字节级副本
- **Teammate**：独立的终端窗格，通过文件邮箱通信
- **Worktree**：独立的 git worktree，每个 Agent 隔离分支

**OpenAI 的 SDK：**
- **Agent 作为工具**：专家处理有边界的子任务
- **交接**：专家完全接管

**LangGraph**：子 Agent 作为嵌套状态图

### 3.12 生命周期管理

管理 Agent 初始化、会话状态、终止条件以及中断恢复。Claude Code 使用 git 提交作为检查点，进度文件用于跨会话的结构化状态跟踪。

## 4. 执行循环：组件如何协同工作

文章图解了一个 7 步循环：

```
┌─────────────────────────────────────────────────────────┐
│  步骤 1: 提示词组装                                      │
│  系统提示词 + 工具模式 + 记忆 + 历史 + 用户消息。         │
│  重要上下文放在开头和结尾。                              │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  步骤 2: LLM 推理                                       │
│  组装提示词 → 模型 API → 生成的 token                    │
│  （文本、工具调用或两者兼有）                             │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  步骤 3: 输出分类                                       │
│  无工具调用 → 结束（最终响应）                           │
│  有工具调用 → 进入执行                                  │
│  请求交接 → 更新 Agent，重启循环                         │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  步骤 4: 工具执行                                       │
│  验证参数 → 检查权限 → 沙箱执行 → 捕获结果。              │
│  只读操作并发执行；变更操作串行执行。                      │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  步骤 5: 结果打包                                       │
│  将工具结果格式化为 LLM 可读的消息。                      │
│  捕获错误并作为错误结果返回，以便模型自我修正。              │
└──────────────────────────┬──────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  步骤 6: 上下文更新                                     │
│  将结果追加到对话历史。                                  │
│  如果接近窗口限制 → 触发压缩。                            │
└──────────────────────────┬──────────────────────────────┘
                           ↓
                    循环：返回步骤 1
```

**终止条件是分层的：**
- 模型生成没有工具调用的响应
- 超过最大轮次限制
- Token 预算耗尽
- 护栏断路器触发
- 用户中断
- 返回安全拒绝

**规模变化**：一个简单问题可能只需要 1-2 轮。复杂的重构任务可能链接数十次工具调用，跨越多轮。

## 5. 真实世界的框架实现

### 5.1 Anthropic：Claude Agent SDK 与 Claude Code

**核心哲学**：薄框架，模型承担繁重工作。

**Claude Agent SDK** 通过单个 `query()` 函数暴露框架，创建 Agent 循环并返回流式消息的异步迭代器。运行时是一个 **"笨循环"**——所有智能都在模型中。

**Claude Code** 使用 **Gather-Act-Verify 循环**：
1. **收集**：搜索文件、阅读代码
2. **行动**：编辑文件、运行命令
3. **验证**：运行测试、检查输出
4. **重复**

**多会话连续性**：初始化 Agent 设置环境（初始化脚本、进度文件、功能列表、初始 git 提交），然后后续每个会话中的编码 Agent 读取 git 日志和进度文件来自我定位，选择最高优先级的未完成功能，进行工作，提交并编写摘要。文件系统在上下文窗口之间提供连续性。

### 5.2 OpenAI：Agents SDK 与 Codex

**核心哲学**："代码优先"——工作流逻辑用原生 Python 表达，而非图形 DSL。

**OpenAI Agents SDK** 通过 `Runner` 类实现框架，支持三种模式：异步、同步和流式。

**Codex 三层架构：**
1. **Codex Core**：Agent 代码 + 运行时
2. **App Server**：双向 JSON-RPC API
3. **客户端界面**：CLI、VS Code、Web 应用

**关键洞察**：所有界面共享相同的框架，这就是为什么 *"Codex 模型在 Codex 界面上比在通用聊天窗口中感觉更好。"* 框架才是差异化的关键，而非仅仅是模型。

### 5.3 LangChain 与 LangGraph

**演进**：LangGraph 从 LangChain 的 `AgentExecutor` 演进而来，该组件在 v0.2 中被弃用，因为难以扩展且缺乏多 Agent 支持。

**LangGraph 状态图模型**：两个节点（`llm_call` 和 `tool_node`）通过条件边连接：
- 有工具调用 → 路由到 `tool_node`
- 无工具调用 → 路由到结束

**LangChain 的 Deep Agents**：明确使用"Agent 框架"这一术语——内置工具、通过 `write_todos` 工具进行规划、用于上下文管理的文件系统、子 Agent 派生和持久化记忆。

### 5.4 CrewAI

**架构**：基于角色的多 Agent 系统，包含三个核心概念：
- **Agent**：围绕 LLM 的框架，由角色、目标、背景故事和工具定义
- **Task**：工作单元
- **Crew**：Agent 的集合

**Flows 层**：添加了"确定性骨干 + 需要智能的地方注入智能"——管理路由和验证，而 Crew 负责自主协作。

### 5.5 AutoGen → Microsoft Agent Framework

**架构**：三层设计（Core、AgentChat、Extensions）

**五种编排模式：**
1. 顺序
2. 并发（扇出/扇入）
3. 群聊
4. 交接
5. **Magentic**：管理 Agent 维护动态任务账本，协调专家

## 6. 脚手架隐喻与协同进化原则

### 6.1 隐喻

建筑脚手架是临时基础设施，使工人能够构建原本无法到达的结构。它不做建筑工作。但没有它，工人无法到达上层。

**关键洞察**：建筑完成后脚手架被拆除。随着模型改进，框架复杂性应该降低。

**Manus 示例**：六个月内重建了五次，每次重写都移除复杂性：
- 复杂的工具定义 → 通用 shell 执行
- "管理 Agent" → 简单的结构化交接

### 6.2 协同进化原则

模型现在是在循环中包含特定框架的情况下进行后训练的。Claude Code 的模型学会了使用它所训练的特定框架。**改变工具实现可能会因这种紧密耦合而降低性能。**

### 6.3 未来验证测试

> *如果性能随着更强大的模型而提升，而不需要增加框架复杂性，则设计是合理的。*

这表明该领域正朝着随着模型改进而使用更薄框架的方向发展——但框架本身不会消失。即使是最有能力的模型也需要某种东西来管理其上下文窗口、执行其工具调用、持久化其状态并验证其工作。

## 7. 每个框架架构师面临的七个架构决策

### 7.1 单 Agent vs. 多 Agent

**规则**：首先最大化单个 Agent。多 Agent 系统增加开销（路由的额外 LLM 调用、交接期间的上下文丢失）。

**何时拆分：**
- 工具过载超过约 10 个重叠工具
- 存在明显分离的任务领域

### 7.2 ReAct vs. Plan-and-Execute

| 方法 | 特点 |
|------|------|
| **ReAct** | 在每一步交错推理和行动。灵活但每步成本更高。 |
| **Plan-and-Execute** | 将规划与执行分离。 |
| **LLMCompiler** | 报告比顺序 ReAct 快 **3.6 倍**。 |

### 7.3 上下文窗口管理策略

五种生产方法（如第 3.4 节详述）：
1. 基于时间清理
2. 对话总结
3. 观察掩码
4. 结构化笔记
5. 子 Agent 委托

### 7.4 验证循环设计

| 类型 | 方法 | 权衡 |
|------|------|------|
| **计算型** | 测试、linter | 确定性的真值，无延迟 |
| **推理型** | LLM 作为裁判 | 捕获语义问题，但增加延迟 |

**Martin Fowler 的表述**：指南（前馈，行动前引导）vs. 传感器（反馈，行动后观察）。

### 7.5 权限与安全架构

| 模式 | 特点 |
|------|------|
| **宽松** | 快速但有风险；自动批准大多数操作 |
| **严格** | 安全但缓慢；每项操作都需要批准 |

选择取决于部署上下文。

### 7.6 工具范围策略

**反直觉发现**：更多工具通常意味着更差的性能。

- **Vercel**：从 v0 移除 80% 的工具，结果更好
- **Claude Code**：通过延迟加载实现 95% 的上下文减少

**原则**：仅暴露当前步骤所需的最小工具集。

### 7.7 框架厚度

**频谱：**
- **薄框架**（Anthropic 的赌注）：模型改进处理复杂性
- **显式控制**（基于图的框架）：更多框架逻辑，更多控制

**Anthropic 的方法**：随着新模型版本内部化这些能力，定期从 Claude Code 框架中删除规划步骤。

## 8. 关键发现总结

1. **框架是差异化的关键**：使用相同模型的两种产品可能因框架设计而产生截然不同的性能。TerminalBench 证据显示，仅框架更改就能产生 20+ 排名位置的变化。

2. **"Agent"是涌现行为，而非模型**：当实践者说"我构建了一个 Agent"，他们的意思是构建了一个框架并将其指向一个模型。

3. **上下文管理是 Agent 悄然失败的地方**：由于"Lost in the Middle"效应，性能下降 30%+。存在五种生产策略：压缩、观察掩码、JIT 检索、结构化笔记和子 Agent 委托。

4. **验证循环区分演示和生产**：Boris Cherny：让模型有能力验证其工作可以将质量提高 2-3 倍。

5. **错误累积**：每步 99% 成功率的 10 步过程仍然只有约 90.4% 的端到端成功率。四种错误类型需要不同策略。

6. **多 Agent 增加开销**：路由的额外 LLM 调用和交接期间的上下文丢失。仅在工具过载超过约 10 个重叠工具时拆分。

7. **工具范围是反直觉的**：更多工具通常意味着更差的性能。Claude Code 通过延迟加载实现 95% 的上下文减少。

8. **协同进化很重要**：模型是针对特定框架进行后训练的。改变工具实现可能因紧密耦合而降低性能。

9. **脚手架应随着模型改进而减少**：Manus 六个月内重建了 5 次，每次都移除复杂性。未来验证测试：性能是否随着更强大的模型而扩展，而不增加框架复杂性？

10. **框架不是商品层**：这里才是硬工程所在——将上下文作为稀缺资源管理、设计验证循环、构建记忆系统，以及在模型与框架复杂性之间做出架构决策。

## 10. 不足与建议的后续步骤

1. **具体代码示例**：本文侧重于概念。为 12 个组件中的每一个添加实际实现模式将增加实际价值。

2. **基准测试方法论**：TerminalBench 声明（LangChain 跃升 20+ 位置）缺乏可验证的方法论。与实际 TerminalBench 2.0 结果交叉引用将增强可信度。

3. **量化的工具范围权衡**：虽然文章指出"Vercel 移除了 80% 的工具，结果更好"，但没有提供指标。找到实际性能数据将加强这个反直觉的发现。

4. **比较框架基准**：对不同框架（Claude Code vs. OpenAI SDK vs. LangGraph）使用标准化任务进行系统性框架性能比较将很有价值。

5. **时间演变**：模型现在针对特定框架进行后训练的声明表明快速协同进化。追踪框架设计如何随模型版本变化将很有启发性。
