## 1. 问题：人类注意力是瓶颈

> "The bottleneck in software engineering nowadays is not intelligence. It's now limited by human attention."

即使是最优秀的工程师，一次也只能完成几项任务。他们可能有 50 个特性的待办清单，但由于每项任务都需要关注，每天只能推进少量。

**关键洞察**：人类决定做什么，系统决定如何做。Agent 可以连续工作数小时甚至数天，你回来时工作就完成了。

---

## 2. 五种多代理框架

Luke 提出了一个简单的分类法，包含五种前沿多代理框架：

| 框架 | 描述 | 特点 |
|------|------|------|
| **委托 (Delegation)** | 一个 agent 派生另一个并等待响应 | 最简单的多代理通信形式 |
| **创建者-验证者 (Creator-Verifier)** | 一个 agent 构建，另一个检查 | 职责分离，"新鲜"验证者更容易发现问题 |
| **直接通信 (Direct Communication)** | Agent 之间无中心协调器直接通信 | 难以正确实现，状态分散 |
| **谈判 (Negotiation)** | Agent 通过共享资源进行通信 | 不必是对抗性的，最佳场景是"正和博弈" |
| **广播 (Broadcast)** | 一个 agent 向多个发送信息 | 对状态更新、共享约束至关重要 |

## 3. Missions：三角色架构

**Missions** 是 Factory 的答案，它将四种框架（委托、创建者-验证者、广播、谈判）组合成一个工作流。

### 三种角色

1. **编排器 (Orchestrator)**
   - 处理规划
   - 充当"共鸣板"，提出正确的战略性问题
   - 检查需求是否清晰
   - 生成包含功能、里程碑和**验证合约**的计划

2. **工作者 (Workers)**
   - 处理实现
   - 拥有干净的上下文，无累积负担
   - 读取规范 → 实现功能 → 提交 Git
   - 允许下一个工作者继承干净的状态

3. **验证器 (Validators)**
   - 处理验证
   - 运行 lint、类型检查、测试
   - 执行代码审查
   - **关键**：验证行为而非仅验证代码是否正确
   - 像 QA 工程师一样行为，通过 computer use 与应用交互

### 验证合约 (Validation Contract)

> "It's written during planning before any code and it defines correctness independently of implementation."

验证合约在规划期间编写，在任何代码之前定义"完成"的含义。复杂项目可能有数百个断言，每个功能分配一个或多个必须满足的断言。

**两种验证器**：
- **Scrutiny 验证器**：运行测试套件、类型检查、lint，为每个已完成的功能生成专用代码审查 agent
- **用户测试验证器**：像 QA 工程师一样行为——启动应用、通过 computer use 与之交互、填写表单、检查页面是否正确渲染

## 4. 结构化交接 (Structured Handoffs)

当工作者完成功能时，它不会只说"我完成了"。它填写**结构化交接文档**，详细说明：
- 完成了什么
- 留下了什么
- 运行了哪些命令及退出码
- 发现了什么问题
- 是否遵守了编排器为该工作者定义的程序

这使得系统能够**自我修复**——错误在里程碑边界被捕获，纠正工作被重新调整范围，Mission 重新回到正轨。

> "Not by hoping that agents remember what happened but by forcing them to write it down."

**最长的 Mission 运行了 16 天**，比完整的 sprint 还长。团队认为可以运行 30 天。这只有通过这种结构才成为可能。

---

## 5. 串行执行优于并行

Luke 提出了一个违反直觉的观点：

> "The most obvious choice is like parallelism... But we tried that and it doesn't really work for tasks in the like software dev domain because agents conflict."

并行的问题：
- Agent 互相踩踏对方的更改
- 重复工作
- 做出不一致的架构决策
- 协调开销最终抵消了速度收益

**Missions 的方案**：
- 功能**串行运行**
- 每个功能内部允许对**只读操作**进行并行化（如搜索代码库、研究 API）
- 验证器内部也对只读操作进行并行化（如代码审查）

这看起来更慢，但错误率大幅下降。当你有运行多天的任务时，**正确性会复合**。

## 6. Mission Control：任务监控

对于持续多天的任务，标准聊天界面不起作用。Luke 团队构建了 **Mission Control**——一个专用仪表板视图，可以：
- 查看完成进度
- 查看预算消耗
- 实时查看当前工作者在做什么
- 查看交接摘要详情
- 查看验证者发现了什么

这让你可以**异步运行 Missions**，作为项目经理监督实现，或者干脆去和朋友聚会。

## 7. 为每个角色选择合适的模型：Droid Whispering

> "Everything here sort of assumes one thing... you're using the right model in each role."

不同角色需要不同的模型能力：

| 角色 | 需求 | 推荐模型特点 |
|------|------|-------------|
| 规划 (Planning) | 慢而仔细的推理 | 强大的推理能力 |
| 实现 (Implementation) | 快速的代码流利度和创造力 | 快速代码生成 |
| 验证 (Validation) | 精确的指令遵循 | 严格的指令跟随 |

**关键洞察**：没有单一模型或模型提供者在所有三个方面都是最佳的。

团队将此技能称为 **"Droid Whispering"**——你需要能够心理建模不同 LLM 如何交互、它们在哪里失败、这些失败如何在多天运行中复合，然后做出明智的选择将哪个模型放在哪个座位上。

**结构性优势**：
- 验证可以使用不同的模型提供者，以确保不受相同训练数据的影响
- 使用开源模型也能成功运行 Missions，因为验证合约和里程碑检查点提供了结构性保障
- 随着模型持续专业化，将正确模型放在正确座位的能力成为**复合优势**

## 8. 构建系统的艺术：随模型升级而改进

> "We had to make this system get better with every model improvement."

这意味着几乎所有编排逻辑都在**prompts 和 skills 中定义**，而不是硬编码状态机。

- 失败分解、特性分解、失败处理都在约 **700 行文本**中
- 其中四句话可以显著改变执行策略
- 工作器行为由编排器为每个 mission 定义的 skills 驱动
- 唯一确定性逻辑非常薄，专注于让模型做它们最擅长的事

**Missions 确保纪律，模型提供智能**——使用它们已经熟悉的原语，如 agents.md、skills 等。

---

## 9. 软件工程的转变经济学

> "The economics are sort of changing."

**之前**：5 人工程师团队可能一次处理 10 个工作流。
**现在**：借助 Missions，可以将其提升到 **30 个**。

团队可以专注于有趣的问题——架构、产品决策——而不是担心执行本身。

**关键结果**：
- 代码库最终比开始时更干净
- 50% 的代码行是测试
- 90% 的代码被测试覆盖
- 测试驱动开发不是建议，而是系统固有的一部分

---

## 总结：关键要点

1. **人类注意力是真正瓶颈**——让人类决定做什么，让系统处理如何做
2. **Missions = 委托 + 创建者-验证者 + 广播 + 谈判** 的组合
3. **三角色系统**：编排器（规划）、工作者（实现）、验证器（验证）
4. **验证合约**在编码前定义成功标准，独立于实现
5. **结构化交接**防止上下文丢失，支持长时间运行
6. **串行执行**对软件开发任务更有效
7. **每个角色选择正确模型**是复合优势
8. **系统应随模型改进而改进**，而非被淘汰

> "Strategies aren't enough. You need the connective tissue—structured handoffs, the right model in each role, and an architecture that improves with each model generation."
