# Running an AI-native engineering org

## 演讲概要

**标题**: Running an AI-native engineering org
**演讲者**: Fiona Fung，Claude Code 工程总监
**链接**: https://www.youtube.com/watch?v=igO8iyca2_g
**主题**: 当 AI 原生编程从个人工具成为团队默认实践，组织流程面临的挑战与应对

---

## 核心观点

### 1. 瓶颈已转移

过去工程带宽（engineering bandwidth）是最昂贵的资源，无数流程（规划、代码审查、所有权划分）都围绕这一瓶颈设计。但现在：

- **编码不再是瓶颈**：Claude Code 团队的代码生成速度极快，吞吐量大幅提升
- **新瓶颈浮现**：验证（verification）、审查（review）、跨职能协作、安全合规

### 2. 需要重写的团队规范

#### 规划（Planning）

- 从六个月路线图转变为 **JIT（即时）规划**，类似 JIT 编译
- 用 **PR 而非文档** 进行技术讨论：`"有个想法？去原型实现"` 而不是 `"先写设计文档"`
- 减少设计文档，但**加倍投入验证环节**——自动化测试左移更早发现问题

#### 技术争论

- 受益于 AI 生成能力，可以快速产出**三个 PR 版本**对比讨论
- 不再依赖白板辩论，而是直接用代码方案支撑决策
- 核心原则：**构建廉价，争论昂贵**——确保团队有良好的技术对齐文化

#### 代码审查

- **Claude 负责**：样式检查、lint、PR 反馈请求、甚至自动修复 bug 和添加测试
- **人类专家负责**：法律合规、风险容忍、安全敏感代码、产品品味
- 信任但验证（Trust but verify）

#### 代码所有权

- "谁改了这代码？"这个问题变得模糊
- 更好的做法是**深挖你真正想问的问题**：是追溯 bug？是找专家解答客户问题？还是获取上下文？
- 找到问题本质后，用 Claude 自动化回答

### 3. 团队组成的变化

两种关键人才：

- **有产品感的创意构建者**：好奇心强， passion about solving problems
- **深度系统专家**：如分布式系统——构建 Claude Code 远程运行时仍需要这类人

不再过度看重：

- **原始吞吐量**（raw throughput）——因为 AI 已经大幅提升了效率

跨职能gap被填补：

- 工程师可以用 Claude 做内容设计（survey 文案等）
- PM 可以大量写代码
- AI 模糊了传统角色边界

### 4. 组织形态

- **保持扁平**：让团队保持敏捷，减少层级带来的上下文切换
- **经理先做 IC**：所有 Claude Code 经理先以个人贡献者身份入职，建立技术信誉
- **狗食法（Dogfooding）**：领导者自己要天天使用产品，保持动手能力

### 5. 团队规范推行方式

**必须做（Must do）**：

- 每个人都用 Claude Code（包含跨职能伙伴）
- Claudify 一切可以自动化的流程
- 明确授权**杀死旧流程**

**给予空间（Give room）**：

- 每个 pod（小组）有高度自主权决定自己的 triage、planning rituals、stand-ups、on-call 等
- 不强制指定"你必须自动化这个"

## 成功信号（可衡量指标）

| 指标 | 趋势 |
|------|------|
| 新人上手时间（Onboarding ramp-up）| 大幅缩短 |
| PR 周期时间（PR cycle time）| 缩短 |
| Claude 辅助提交占比（Cloud-assisted commits）| 上升 |
| 代码质量和可靠性 | 持续关注（警惕唯 throughput 论） |

## 仍待探索的问题

1. **移动端组织**：当工程师可以更高效跨平台工作时，iOS/Android 团队划分还合理吗？
2. **自动化审查边界**：快速与安全之间的平衡点在哪里？模型能力在进步，这个平衡也会变化
3. **角色模糊后的平等生产力**：如何确保所有人都有成就感

## 一句话行动建议

> **找出你最嘈杂（noisiest）的工作流**——可能是最贵的、或大家都不喜欢的——然后问自己：它还在服务于它的初衷吗？能自动化吗？能简化吗？能取消吗？
