# The Anatomy of an Agent Harness

> **来源**: Akshay Pachaar (@akshay_pachaar)  
> **URL**: https://x.com/akshay_pachaar/status/2041146899319971922  
> **发布日期**: 2026年4月6日

## 文章概述

本文深入探讨了 AI Agent 的核心基础设施——**Agent Harness**，系统性地拆解了将"无状态"LLM转变为智能 Agent 所必需的完整软件架构。

**核心论点**：生产级 Agent 的表现差异不在于底层模型，而在于围绕模型的 Harness（架套/基础设施）设计。

**关键证据**：LangChain 仅通过改变 Harness 架构（模型和参数完全不变），就在 TerminalBench 2.0 上从第 30 名跃升至第 5 名。

---

## 一、什么是 Agent Harness？

**定义**：Harness 是包裹在 LLM 之上的完整软件基础设施，包括：编排循环(Orchestration Loop)、工具(Tools)、记忆(Memory)、上下文管理(Context Management)、状态持久化(State Persistence)、错误处理(Error Handling)和护栏(Guardrails)。

**核心公式**：`Agent = Model + Harness`

**精准类比**（Beren Millidge, 2023）：
- 原生 LLM ≈ 没有内存、硬盘、I/O设备的 CPU
- 上下文窗口 = 内存（快但容量有限）
- 外部数据库 = 硬盘（大但速度慢）
- 工具集成 = 设备驱动程序
- **Harness = 操作系统**

**LangChain Vivek Trivedy 的定义**："如果你不是模型本身，那你就是 Harness。"

## 三、生产级 Harness 的 12 个核心组件

### 1. 编排循环 (Orchestration Loop)
- **核心**：TAO循环（Thought-Action-Observation），即 ReAct 循环
- **本质**：通常只是一个 `while` 循环，但复杂性在于循环要处理的各种状态和逻辑
- **Anthropic 的定位**：他们的运行时是"笨循环"，所有智慧在模型中，Harness 只管理回合切换

### 2. 工具 (Tools)
- **作用**：Agent 的"双手"
- **处理流程**：注册 → 格式校验 → 参数提取 → 沙箱执行 → 结果捕获 → 格式化为观察结果
- **Claude Code** 提供六大类工具：文件操作、搜索、执行、网页访问、代码分析、子Agent创建
- **OpenAI Agents SDK** 支持：函数工具(@function_tool)、托管工具、MCP服务器工具

### 3. 记忆 (Memory)
- **短期记忆**：单次会话中的对话历史
- **长期记忆**：跨会话持久存在（Claude Code用项目文件和`memory.md`；LangGraph用命名空间JSON；OpenAI用SQLite/Redis）
- **Claude Code三层架构**：
  - 轻量级索引（每条约150字符，始终加载）
  - 按需调用的详细主题文件
  - 仅通过搜索访问的原始对话记录
- **核心原则**：Agent 将记忆视为"提示"，行动前必须根据实际状态验证

### 4. 上下文管理 (Context Management)
- **核心问题**：上下文腐烂（Context Decay）
  - 关键信息处于窗口中间时，模型表现下降30%以上（斯坦福"迷失在中间"现象）
  - 即使百万级Token窗口，随上下文增长指令遵循能力也会退化

- **生产环境应对策略**：
  - **压缩**：接近限制时总结对话（Claude Code保留架构决策和未修复Bug，丢弃冗余工具输出）
  - **观察掩码**：隐藏旧工具输出，保留工具调用记录
  - **即时检索**：只保留轻量级标识符，动态加载数据
  - **子Agent委托**：深度探索后返回1000-2000 Token的浓缩摘要

- **Anthropic指南**：找到能最大化达成目标概率的、信号最强的最小Token集合

### 5. 提示词构建 (Prompt Construction)
- 层级化构建：系统提示词 → 工具定义 → 记忆文件 → 对话历史 → 当前用户消息
- **OpenAI Codex优先级栈**：服务器控制消息 → 工具定义 → 开发者指令 → 用户指令 → 对话历史

### 6. 输出解析 (Output Parsing)
- 现代 Harness 依赖**原生工具调用**（结构化`tool_calls`对象）
- 检查逻辑：是否有工具调用？有则执行并继续；无则输出为最终答案
- 支持 Pydantic 模型进行模式约束

### 7. 状态管理 (State Management)
- **LangGraph**：状态在图形节点中流动的类型化字典，支持Checkpointing和时间旅行调试
- **OpenAI四种策略**：应用内存、SDK会话、服务器端API、轻量级响应ID链
- **Claude Code**：将Git提交作为存档点，进度文件作为结构化草稿纸

### 8. 错误处理 (Error Handling)
- **关键数学**：10个步骤，每步99%成功率 → 整体成功率仅90.4%（错误会滚雪球）
- **LangGraph四类错误**：
  - 临时性（带延迟重试）
  - 模型可恢复（将错误作为工具消息返回，让模型自我调整）
  - 用户可修复（暂停等待人类干预）
  - 意外错误（上报调试）

### 9. 护栏与安全 (Guardrails and Safety)
- **OpenAI SDK三层**：
  - 输入护栏（第一个Agent运行时检查）
  - 输出护栏（检查最终结果）
  - 工具护栏（每次工具调用前检查）
  - 触发"绊网"则立即停止
- **Anthropic**：将"权限执行"与"模型推理"分离——模型决定想做什么，但Harness决定允许做什么

### 10. 验证循环 (Verification Loops)
- **三种方法**：
  - 基于规则的反馈（测试、代码检查）
  - 视觉反馈（Playwright截取UI截图）
  - LLM-as-judge（由子Agent评估输出）
- **Boris Cherny（Claude Code创始人）**：让模型验证自己的工作，能让产出质量提升2-3倍

### 11. 子Agent编排 (Subagent Orchestration)
- **Claude Code三种模式**：
  - Fork（复制父级上下文）
  - Teammate（通过文件邮箱通信的独立窗口）
  - Worktree（独立的Git分支）
- **OpenAI**：Agent作为工具（专家处理子任务）或移交（专家接管后续控制权）

## 四、Agent循环的步进式运作

```
┌──────────────────────────────────────────────────────┐
│  第1步: 提示词组装                                    │
│    Harness 构建完整的输入信息                          │
└─────────────────────┬────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────┐
│  第2步: 模型推理                                      │
│    发送给模型API，生成Token（文本或工具调用请求）        │
└─────────────────────┬────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────┐
│  第3步: 输出分类                                      │
│    有工具调用？ → 否 → 循环结束，输出答案               │
│                → 是 → 进入执行阶段                     │
└─────────────────────┬────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────┐
│  第4步: 工具执行                                      │
│    校验参数、检查权限、沙箱运行、捕获结果                │
└─────────────────────┬────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────┐
│  第5步: 结果打包                                      │
│    格式化为模型可读消息，捕获错误供模型自愈              │
└─────────────────────┬────────────────────────────────┘
                      ▼
┌──────────────────────────────────────────────────────┐
│  第6步: 上下文更新                                    │
│    追加到历史记录，必要时触发压缩                       │
└─────────────────────┬────────────────────────────────┘
                      ▼
                 返回第1步
```

## 五、主流框架的实现方式

| 框架 | 实现特点 |
|------|---------|
| **Anthropic (Claude Agent SDK)** | 通过简单`query()`函数暴露Harness，"笨循环"设计 |
| **OpenAI (Agents SDK)** | "代码优先"策略，工作流逻辑直接用Python表达 |
| **LangGraph** | 将Harness建模为显式状态图，强调精细流程控制 |
| **CrewAI** | 基于角色的多Agent协作，"流程层"管理确定性骨干 |
| **AutoGen** | 微软开发，支持顺序执行、群聊、移交、动态任务管理 |

## 六、脚手架比喻

**脚手架是临时性的基础设施**，让工人能触及原本够不到的高度。脚手架本身不盖房子，但没有它，工人上不去高层。

**关键洞察**：房子盖好后，脚手架是要拆除的。随着模型能力提升，Harness的复杂程度应该逐渐降低。

这就是**协同进化原则**：如果Harness设计得好，当模型升级时，不需要增加复杂度，性能就会自动提升。

## 七、Harness的7个关键设计决策

1. **单Agent vs. 多Agent**：先充分挖掘单Agent的潜力；多Agent带来额外开销和信息损耗
2. **ReAct vs. 先规划后执行**：ReAct灵活但成本高；"先规划后执行"速度更快
3. **上下文管理策略**：总结对话 vs. 动态加载
4. **验证循环设计**：硬性代码测试 vs. LLM打分
5. **权限与安全架构**：追求速度自动批准 vs. 追求安全步步确认
6. **工具范围管理**：暴露当前步骤所需的最小工具集往往效果最佳
7. **Harness的厚度**：多少逻辑写死在系统里，多少留给模型发挥

## 八、核心结论

> "Harness不是一个已经解决的问题，也不是一个通用的商品层。它是硬核工程能力的体现。"

**随着模型越来越强，Harness会变薄，但它永远不会消失。** 即使最强大的模型，也需要系统来管理窗口、执行代码、保存状态并验证工作。

**下次当你的Agent表现不佳时，别光顾着抱怨模型，去检查一下你的Harness吧。**
