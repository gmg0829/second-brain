# 不要构建代理，而是构建技能 - Anthropic Skills 范式转变

## 核心观点

Anthropic 的 Barry Zhang 和 Mahesh Murag 提出了一个重要的范式转变：**停止构建代理，开始构建技能**。

尽管 AI 代理在过去一年取得了快速进展，模型智能显著提升，代理框架也趋于成熟，但仍存在一个关键差距：**代理拥有智能和能力，但往往缺乏完成真实工作所需的领域专业知识**。

Skills（技能）是解决这一问题的方案——一种最小化的格式，用于打包可供代理动态加载的程序化知识。这是一种便携、可组合的方法，使单个代理能够跨领域获得能力。

## 问题：专业知识的缺失

### 智能 ≠ 专业知识

演讲者用一个生动的比喻说明问题：

> "你会让谁来报税？是 300 IQ 的数学天才 Mahesh，还是经验丰富的税务专家 Barry？我每次都会选 Barry。我不希望 Mahesh 从第一原则推导出 2025 年的税法。我需要领域专家的稳定执行。"

**当前代理的状态：**

- 拥有卓越的智能

- 能够做出惊人的事情

- 但缺乏关键的领域专业知识

- 无法有效吸收专业经验

- 不会随时间学习

**具体表现：**

- 需要详细指导才能完成任务

- 常常缺少重要的前置上下文

- 执行的一致性不足

- 难以处理领域特定的最佳实践

## 解决方案：Agent Skills

### 什么是 Skills？

**定义：** Skills 是组织化的文件集合，用于打包可组合的程序化知识供代理使用。

**更直白地说：它们就是文件夹。**

### 为什么选择如此简单的设计？

这种简单性是刻意为之的：

1. **任何人都能创建和使用** - 只要有计算机，无论是人类还是代理

2. **与现有工具兼容** - 可以在 Git 中版本控制、存储在 Google Drive、打包分享给团队

3. **利用成熟的原语** - 文件系统是我们使用了几十年的可靠工具

### Skills 与传统工具的对比

**传统工具的问题：**

- 说明写得不好，模糊不清

- 当模型遇到困难时无法修改工具

- 陷入"冷启动"困境

- 始终占用上下文窗口

**代码/脚本的优势：**

- **自文档化** - 代码本身说明其功能

- **可修改** - 代理可以调整和改进

- **按需加载** - 存储在文件系统中，仅在需要时使用

- **更高效** - 避免重复编写相同逻辑

**实际示例：**

Anthropic 团队发现 Claude 反复编写相同的 Python 脚本来为幻灯片应用样式。解决方案很简单：

```python
# 将脚本保存在技能中
apply_slide_styling.py

# 现在只需运行脚本
python apply_slide_styling.py --input slides.pptx
```

结果：更一致、更高效的执行。

## "代码即一切"范式

### 范式转变

**旧观念：**

- 不同领域的代理看起来非常不同

- 每个领域需要自己的工具和框架

- 每个用例需要单独的代理

**新认知：**

- 代理的底层结构比想象中更通用

- **代码不仅仅是一个用例，而是通往数字世界的通用接口**

### Claude Code 的启示

在构建 Claude Code 后，团队意识到它实际上是一个**通用代理**。

**生成财务报告的例子：**

1. **调用 API** 获取数据并进行研究

2. **在文件系统中组织** 数据

3. **用 Python 分析** 数据

4. **综合洞察** 并生成报告

所有这些都通过代码完成！核心框架可以精简到只需要 **Bash 和文件系统**，具有极大的可扩展性。

### 但仍存在挑战

虽然技术栈简化了，但新问题出现了：**领域专业知识**。

通用能力需要与特定领域的知识相结合。

## Skills 架构设计

### 1. 核心结构

```plaintext
skill-name/
├── skill.md              # 核心指导和目录
├── scripts/              # 工具脚本
│   ├── tool1.py
│   ├── tool2.sh
│   └── helper.js
├── examples/             # 示例和模板
├── docs/                 # 详细文档
└── assets/               # 其他资源
```

### 2. 渐进式披露

**问题：** 技能可能包含大量信息，我们需要保护上下文窗口以支持数百个技能。

**解决方案：** 渐进式披露

**运行时行为：**

```plaintext
初始状态：
└── skill-metadata.json  (仅显示元数据给模型)

需要使用时：
├── 读取 skill.md        (核心指导和目录)
└── 按需读取其他文件     (脚本、文档等)
```

这种设计使得：

- 可以装载数百甚至数千个技能

- 真正实现可组合性

- 仅在需要时消耗上下文

### 3. 脚本作为工具

Skills 中的脚本就是工具，但具有独特优势：

**特性：**

- 代理可以查看和理解代码

- 可以根据需要修改

- 可以重用和组合

- 自带文档（代码即文档）

**示例场景：**

```bash
# 技能中的脚本
fetch_weather.sh --location "San Francisco"

# 代理可以：
1. 查看脚本了解其功能
2. 根据需要调整参数
3. 将其与其他脚本组合
4. 验证输出并迭代
```

## 快速增长的生态系统

自发布 5 周以来，已有**数千个技能**被创建，生态系统迅速扩展。

### 三种类型的技能

#### 1. 基础技能（Foundational Skills）

**目的：** 赋予代理新的通用或领域特定能力

**示例：**

**文档技能（Anthropic 开发）：**

- 创建和编辑专业质量的办公文档

- Word、Excel、PowerPoint 等

**科学研究技能（Cadence 开发）：**

- EHR（电子健康记录）数据分析

- 使用常见的 Python 生物信息学库

- 性能优于基础模型

#### 2. 第三方技能（Third-Party Skills）

**目的：** 合作伙伴构建技能以增强 Claude 与其产品的集成

**示例：**

**Browserbase 的 Stagehand 技能：**

- 开源浏览器自动化工具

- 使 Claude 能够更有效地浏览网页

- 在浏览器中完成工作

**Notion 技能：**

- 理解用户的 Notion 工作区

- 在整个工作区进行深度研究

- 更好地组织和检索信息

#### 3. 企业技能（Enterprise Skills）

**目的：** 为组织构建公司和团队特定的技能

这是演讲者看到**最多兴奋和吸引力**的领域。

**使用案例：**

**Fortune 100 公司：**

- 教授代理组织最佳实践

- 处理独特的内部软件使用方式

- 编码特定的业务流程

**大型开发者生产力团队：**

- 服务数千甚至数万名开发者

- 部署 Claude Code 等代理

- 教授代码风格和最佳实践

- 规范内部开发工作流程

**关键洞察：**

- **非技术人员也在创建技能** - 财务、招聘、会计、法律等职能的人员

- 这验证了技能让通用代理对非编码工作更加可访问

## 新兴趋势

### 1. 技能正变得更加复杂

**初期：**

- 简单的 [skill.md](http://skill.md) 文件

- 基本提示和指导

**现在：**

- 打包软件

- 可执行文件和二进制文件

- 代码、脚本、资源

- 构建时间：几分钟到几小时

**未来：**

- 像传统软件一样

- 需要数周或数月开发

- 需要持续维护

### 2. 与 MCP 生态系统互补

**关系：**

- MCP 服务器提供**外部连接**（工具和数据）

- Skills 提供**专业知识**（如何使用这些工具）

**协同作用：**

```plaintext
Skills 编排多个 MCP 工具的工作流
    ↓
将外部数据和连接整合到复杂任务中
    ↓
MCP = 连接 / Skills = 专业知识
```

### 3. 非技术人员创建技能

**重要性：** 这是技能价值主张的早期验证

**意义：**

- 技能使通用代理对日常工作更易访问

- 不仅限于开发者和技术人员

- 各职能部门都能扩展代理能力

- 民主化 AI 代理开发

## 通用代理的未来架构

### 架构趋同

演讲者认为我们正在向一个通用架构收敛：

```plaintext
┌─────────────────────────────────────┐
│         代理循环 (Agent Loop)        │
│   管理模型的内部上下文和 token 流    │
└─────────────┬───────────────────────┘
              │
┌─────────────┴───────────────────────┐
│      运行时环境 (Runtime)            │
│   • 文件系统                         │
│   • 代码读写能力                     │
└─────────────┬───────────────────────┘
              │
        ┌─────┴─────┐
        │           │
┌───────┴──┐   ┌───┴────────┐
│   MCP    │   │   Skills   │
│  服务器   │   │    库      │
│          │   │            │
│ 外部工具  │   │ 数百/数千  │
│ 和数据    │   │ 按需加载   │
└──────────┘   └────────────┘
```

### 核心组件

**1. 代理循环**

- 管理模型的内部上下文

- 控制 token 输入输出

**2. 运行时环境**

- 提供文件系统

- 支持代码读写

**3. MCP 服务器**

- 来自外部世界的工具和数据

- 使代理更相关和有效

**4. Skills 库**

- 数百或数千个技能

- 运行时动态加载

- 根据特定任务选择

### 实际应用

**赋予代理新领域能力的新模式：**

```plaintext
选择合适的 MCP 服务器
    +
选择合适的 Skills 库
    =
新领域的即时能力
```

**Anthropic 的实践：**

发布 Skills 后 5 周内，立即推出：

- **金融服务** 产品

- **生命科学** 产品

每个都配备：

- 一组 MCP 服务器

- 一组 Skills

结果：Claude 立即对这些领域的专业人士更有效。

## 未来发展方向

### 像对待软件一样对待 Skills

随着 Skills 变得更加复杂，需要更好的工具支持。

#### 1. 测试和评估

**需求：**

- 确保代理在正确时间加载和触发技能

- 验证代理使用技能完成正确任务

- 测量配备技能的代理的输出质量

- 确保符合预期行为

**目标：** 像测试软件一样测试技能

#### 2. 版本控制

**需求：**

- 随着技能演进，代理行为也会演变

- 需要清晰追踪变化

- 建立清晰的版本谱系

**示例：**

```plaintext
skill-v1.0.0 → behavior A
skill-v1.1.0 → behavior B (improved)
skill-v2.0.0 → behavior C (major change)
```

#### 3. 依赖关系

**概念：** 技能应能明确依赖和引用：

- **其他技能** - 组合和重用

- **MCP 服务器** - 所需的外部连接

- **环境中的依赖和包** - Python 包、npm 模块等

**好处：**

- 使代理在不同运行时环境中更可预测

- 多个技能的组合性增强

- 从代理中引发更复杂和相关的行为

### 目标

这些功能应该：

- 使技能更易于构建

- 更易于集成到代理产品中

- 不仅限于 Claude - 对整个生态系统开放
