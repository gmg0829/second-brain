## 背景：AI 系统的演进路径

在进入核心理论之前，Barry 梳理了 AI 系统从简单到复杂的三阶段演进：

| 阶段 | 特征 | 现状 |
|------|------|------|
| **简单功能** | 摘要、分类、提取，单次模型调用 | 已成"标配"，不再新奇 |
| **工作流（Workflow）** | 多次模型调用，预定义控制流，决策路径可完整枚举 | 成本可控、确定性强 |
| **Agent** | 自主决定执行路径，基于环境反馈独立运作 | 能力更强，但成本、延迟、错误代价更高 |

**关键区分**：Workflow 的决策树是人为预先映射好的；Agent 则自己决定走哪条路。

## 核心理论一：不要什么都用 Agent 来做

> "Agents thrive in ambiguous problem spaces."

### Agent 的适用判断清单

在决定是否构建 Agent 之前，需通过以下四项检验：

**① 任务复杂度**
- 问题空间是否模糊、难以穷举所有决策分支？
- 如果决策树可以完整画出来 → 用 Workflow 更合算，控制力更强

**② 任务价值**
- Agent 的探索行为会消耗大量 Token
- 任务产生的价值必须能覆盖这个成本
- 反例：高并发、低预算的客服场景（每次任务成本约 0.1 美元）→ Workflow 优先

**③ 关键能力去风险**
- 在全量上线前，必须确保 Agent 的核心能力（如编写代码、调试、错误恢复）已足够健壮
- 任何瓶颈都会成倍放大成本与延迟
- 解法：缩小范围、简化任务、重新验证

**④ 错误代价与可发现性**
- 错误后果越高、越难被发现 → 越难信任 Agent 的自主决策
- 缓解手段：限制操作权限（如只读访问）、增加人工审核节点
- 代价：这些限制同时也压缩了 Agent 的扩展上限

### 最佳实践案例：编程 Agent

编程是 Agent 的理想使用场景，原因：

- 任务本身模糊且复杂，无法穷举决策路径
- 好的代码具有极高商业价值
- 当前模型（如 Claude）在编程工作流的多个环节已表现卓越
- 输出结果可通过单元测试和 CI/CD 流水线**客观验证**

## 核心理论二：保持简单

> "Any complexity up front is really going to kill iteration speed."

### Agent 的最简定义

$$\text{Agent} = \text{模型} \times \text{工具} \times \text{循环}$$

Barry 将 Agent 定义为"在循环中使用工具的模型"，由三个核心要素构成：

```
┌─────────────────────────────────────────┐
│              Agent 三要素                │
├────────────┬────────────┬───────────────┤
│  Environment │   Tools   │ System Prompt │
│    环境      │   工具集   │    系统提示   │
├────────────┼────────────┼───────────────┤
│ Agent 运行  │ 行动接口 + │ 目标、约束、  │
│ 的系统上下文 │ 反馈通道   │ 理想行为定义  │
└────────────┴────────────┴───────────────┘
```

### 迭代优先级原则

1. **第一阶段**：只在环境、工具集、系统提示三个维度上快速迭代
   - 这三者的 ROI 远高于其他任何优化
2. **第二阶段**：核心行为稳定后，再引入优化措施：
   - 缓存轨迹（降低编程 Agent 成本）
   - 并行化工具调用（降低搜索 Agent 延迟）
   - 向用户呈现进度（建立信任感）

**原则**：过早引入复杂性是迭代速度的最大杀手。

### 工具设计是关键决策

在三要素中，环境往往由业务场景决定，真正需要精心设计的是：
- **工具集的边界与粒度**：给 Agent 提供哪些工具？
- **系统提示的质量**：如何准确定义目标与约束？

## 核心理论三：像 Agent 一样思考

> "Put yourself in the agent's context window."

### 核心洞见：Agent 的世界极其有限

尽管 Agent 展现出复杂的行为，但在每一个推理步骤上，它做的事情不过是：

> **对一个极小的上下文窗口（10,000～20,000 Token）运行推理**

这个上下文窗口就是 Agent 认知世界的全部。人类开发者最常犯的错误，是从自己的全知视角来设计 Agent，而忘记了 Agent 看到的世界有多么有限。

### 具体类比："电脑使用 Agent"

想象你是一个负责操作电脑的 Agent：
- 你只能看到**静态截图**，无法感知动态变化
- 你拿到的是一段**写得很差的任务说明**
- 你执行每一次点击，都相当于"**闭上眼睛三到五秒，在黑暗中操作电脑**"
- 结果完全不确定

这个类比揭示了一个"致命盲区"：开发者觉得显而易见的信息（屏幕分辨率、推荐操作路径、边界限制），对 Agent 来说可能完全不存在。

### 实践方法

**方法一：亲身模拟**
- 完整地用 Agent 的视角执行一次任务
- 这会暴露出关键的缺失信息：分辨率、推荐操作、能力限制等
- 避免 Agent 进行"不必要的探索"

**方法二：用 LLM 理解 LLM**

因为我们构建的系统"说人话"，所以可以直接向模型提问来获取 Agent 视角：

```
可以向 Claude 询问的问题：
├── 这段系统提示是否有歧义？指令是否连贯？
├── 这个工具描述是否清晰？Agent 知道什么时候用它吗？
└── 分析这段完整的 Agent 执行轨迹，
    它在哪个决策点出了问题？为什么？
```

> 注意：LLM 分析不能**替代**开发者自己对上下文的理解，而是帮助获得更贴近 Agent 视角的洞察。

## 前沿思考：三大开放问题

Barry 在演讲结尾分享了他认为 AI 工程师需要共同探索的方向：

### 1. 预算感知（Budget Awareness）

**现状**：与 Workflow 不同，当前 Agent 对自身的成本和延迟几乎没有控制感。

**核心问题**：如何为 Agent 定义并动态执行预算约束？
- 时间预算
- Token 预算  
- 金钱预算

解决这一问题，将大幅扩展 Agent 在生产环境中的可部署范围。

### 2. 自进化工具（Self-Evolving Tools）

**现状**：已经可以用模型来迭代优化工具描述。

**愿景**：进一步演化为"元工具"（Meta-Tool）——Agent 能够自主设计和改进自身的工具接口，大幅提升通用性。

### 3. 多 Agent 协作（Multi-Agent Collaboration）

**判断**：Barry 的个人预测是，多 Agent 生产协作将在近期大规模落地。

**协作的核心价值**：
- **并行化**：多个 Agent 同时处理不同子任务
- **关注点分离**：不同 Agent 专注不同职责
- **保护主 Agent 上下文**：避免单一 Agent 上下文窗口过载

**核心开放问题**：Agent 之间如何有效通信？

当前的"用户-助手"同步对话模式过于刚性，需要探索：
- 异步通信机制
- 更多元的 Agent 角色定义

## 理论总结

```
                    如何构建有效的 Agent
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   核心理论一         核心理论二          核心理论三
  不要滥用 Agent      保持简单           像 Agent 思考
          │                │                │
  四项判断清单       三要素 + 迭代优先    上下文窗口视角
  · 复杂度          · 环境              · 感同身受
  · 价值            · 工具集            · LLM 自查
  · 关键能力        · 系统提示          · 暴露盲区
  · 错误代价        先跑通，再优化
```

**一句话总结**：在正确的场景构建 Agent，用最简单的方式启动，然后从 Agent 自己的视角持续改进它。
