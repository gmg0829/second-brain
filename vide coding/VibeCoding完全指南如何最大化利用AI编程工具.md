
## 引言


AI 虽然还不能一次性构建完整的产品,但随着"Vibe Coding"的兴起,这一目标已经越来越近。YC 合伙人 Tom Blomfield 在过去一个月中使用 Claude Code、Windsurf 和 Aqua 等工具构建了多个副项目,深入探索了现代 LLM 的能力边界。从编写全栈应用到只需粘贴错误消息即可调试,AI 正在成为开发过程中真正的协作伙伴。

Vibe Coding 就像一两年前的提示工程——人们每周都在发现新技巧并在社交媒体上分享。最佳实践其实就是专业软件工程师会使用的技术。本指南将分享如何充分利用 AI 编程工具,实现更快速的开发。

## 什么是 Vibe Coding 及其重要性

Vibe Coding 是一种新型编程范式,你不再用代码编程,而是用自然语言编程。这种方式需要以非常详细的方式提供必要的上下文和信息,才能获得良好的结果。

核心理念是:**让 LLM 遵循优秀专业软件开发者会使用的流程**。这是一项可以通过实践不断提升的技能,只要你愿意尝试和学习最佳实践。

## 工具选择:找到适合你的起点

### 初学者工具

**如果你从未编写过代码**,建议从以下工具入手:

- **Replit**:提供易用的可视化界面

- **Lovable**:快速尝试新 UI 的理想选择

这些工具让产品经理和设计师可以直接在代码中实现新想法,而不需要先在 Figma 中设计模型,因为速度实在太快了。

**局限性提醒**:这些工具在 UI 方面表现出色,但当你想更精确地修改后端逻辑时,可能会遇到困难。比如改变一个按钮,后端逻辑可能会莫名其妙地改变。

### 进阶工具

**如果你有编程经验**(即使有些生疏),可以直接使用:

- **Windsurf**:适合需要更长思考时间的复杂任务

- **Cursor**:速度更快,适合前端和全栈开发

- **Claude Code**:在实现和重构方面表现优异

## YC X25 创始人的实战技巧

### 多工具并行策略

**同时使用 Cursor 和 Windsurf**:

- Cursor 速度更快,用于前端和全栈链接

- Windsurf 思考时间更长,用于复杂的后端逻辑

- 在 Windsurf 思考时,可以切换到 Cursor 更新前端

- 甚至可以同时加载两个工具,给它们相同的上下文,让它们生成不同版本的实现,然后选择更好的那个

### IDE 陷入困境时的解决方案

当 AI IDE 无法实现或调试某个问题,陷入循环时:

1. 直接访问 LLM 的网站 UI(如 Claude 或 ChatGPT 网页版)

2. 粘贴你的代码并提出同样的问题

3. 通常能得到 IDE 无法达到的结果

### 测试驱动的 Vibe Coding

**从测试用例开始的反向工作流**:

1. 手工编写测试用例(不使用 LLM)

2. 建立强大的保护规则供 LLM 遵循

3. 让 LLM 自由生成代码

4. 看到测试用例的绿色标志时,工作就完成了

5. 只需关注代码的模块化,无需微观管理

### 充分规划架构

**在使用编码工具之前**:

- 在纯 LLM 环境中花费"不合理的时间"

- 构建详细的范围和架构规划

- 避免让工具在代码库中随意运行,制造不起作用的东西

### 监控 LLM 是否进入"兔子洞"

**识别问题的信号**:

- LLM 不断重新生成代码,看起来很奇怪

- 需要反复复制粘贴错误消息

- 无法真正解决问题

**应对策略**:

- 退一步,提示 LLM:"让我们退后一步,分析为什么会失败"

- 检查是否提供了足够的上下文

- 或者只是运气不好,需要换个请求方式

## 核心最佳实践

### 1. 制定全面计划

**不要一上来就写代码**,而是:

1. 与 LLM 合作编写全面的计划

2. 将计划保存在项目文件夹的 Markdown 文件中

3. 持续参考这个计划

**计划优化**:

- 删除或标记你不喜欢的内容

- 明确标记某些功能为"不做"(太复杂)

- 保留"未来想法"部分,告诉 LLM 这些已考虑但目前超出范围

**分步实施**:

- 按部分逐一实现:"我们现在只做第二部分"

- 检查功能是否正常

- 运行测试

- 提交到 Git

- 让 AI 返回计划并标记该部分为已完成

**现实预期**:目前不要期望模型一次性完成整个产品,尤其是复杂产品。分步进行,确保每一步都有可工作的实现,并提交到 Git 以便必要时回滚。

### 2. 版本控制是你的朋友

**虔诚地使用 Git**:

- 工具虽有恢复功能,但还不够可靠

- 开始新功能前,确保 Git 状态干净

- 这样可以在 AI 出问题时回滚到已知的可工作版本

**避免代码积累**:

- 不要害怕使用 `git reset --hard`

- 如果多次提示 AI 都没效果,说明在积累层层糟糕代码

- 与其反复修改,不如 reset 后用正确方案重新实现

**最佳实践**:即使经过多次提示终于得到解决方案,也应该 reset 代码库,然后在干净的代码库上实现那个清晰的解决方案。

### 3. 编写测试(或让 LLM 编写)

**高层次集成测试优于单元测试**:

- LLM 默认倾向于编写低层次的单元测试

- 更好的做法是编写高层次测试

- 模拟用户点击网站或应用的操作

- 确保功能端到端正常工作

**测试的保护作用**:

- LLM 有个坏习惯:对无关逻辑进行不必要的更改

- 让它修复这里的东西,它却改变了那里的逻辑

- 测试套件可以及早发现这些回归

- 识别 LLM 何时做了不必要的更改,以便 reset 重新开始

**实施建议**:在继续下一个功能前,先编写高层次集成测试。

### 4. LLM 不仅用于编码

**DevOps 工程师**:

- 配置 DNS 服务器(通常令人头疼的任务)

- 通过命令行工具设置 Heroku 托管

- 加速进度 10 倍

**设计师角色**:

- 创建网站 favicon(浏览器窗口顶部的小图标)

- 编写脚本将图像调整为所需的 6 种不同尺寸和格式

- 覆盖所有不同平台的 favicon 需求

**实例**:Tom 使用 Aqua 以 140 字/分钟的速度输入指令(比打字快一倍),甚至整个演讲稿都是用 Aqua 编写的。

### 5. 修复 Bug 的策略

**第一步:复制粘贴错误消息**

- 遇到 bug 时,直接将错误消息粘贴回 LLM

- 可能来自服务器日志文件或浏览器的 JavaScript 控制台

- 通常错误消息就足以让 AI 识别和修复问题

- 不需要解释发生了什么或你的想法

- 简单的错误消息就够了

**未来展望**:很快,主要编码工具将能够自动获取这些错误,无需人工复制粘贴。我们作为"复制粘贴机器"的价值其实很奇怪——我们把思考留给 LLM,但复制粘贴的环节即将消失。LLM 工具将能够跟踪日志或启动无头浏览器检查 JavaScript 错误。

**处理复杂 Bug**:

1. 要求 LLM 在编写代码前思考 3-4 个可能的原因

2. 每次修复尝试失败后,reset 并重新开始

3. 不要在不 reset 的情况下多次尝试修复

4. 添加日志记录——日志是你的朋友

5. 如果实在不行,换个模型(Claude、OpenAI、Gemini)

6. 不同模型在其他模型失败的地方可能会成功

**找到解决方案后**:

- Reset 所有更改

- 在干净的代码库上给 LLM 非常具体的指令

- 精确修复那个 bug

- 避免积累层层垃圾代码

### 6. 编写 LLM 指令

**创建指令文件**:

- Cursor rules、Windsurf rules、Claude markdown 文件

- 每个工具的命名约定略有不同

- 有些创始人编写了数百行指令

- 这使 AI 编码代理更加高效

**资源**:网上有大量关于这些指令文件内容的建议,可以自行查找。

### 7. 文档管理

**本地文档优于在线文档**:

- 将 AI 代理指向在线文档仍然不够稳定

- 有人建议使用 MCP 服务器访问文档(似乎过度复杂)

**更好的方法**:

1. 下载给定 API 集的所有文档

2. 放在工作文件夹的子目录中

3. LLM 可以在本地访问它们

4. 在指令中说明:"在实现之前先阅读文档"

5. 通常会更准确

**附加福利:LLM 作为教师**:

- 对不太熟悉编码语言的人特别有用

- 实现某功能后,让 AI 逐行解释实现

- 学习新技术的绝佳方式

- 比以前浏览 Stack Overflow 好得多

### 8. 复杂功能实现

**独立原型策略**:

对于比你通常信任 AI 实现的更复杂的新功能:

1. 在完全干净的代码库中作为独立项目进行

2. 获得一个小型参考实现

3. 不受现有项目复杂性的影响

4. 或者从 GitHub 下载别人编写的参考实现

**集成到主项目**:

- 让 LLM 指向这个参考实现

- 告诉它在更大的代码库中重新实现时遵循该实现

- 效果出奇地好

**架构建议**:

- 小文件和模块化是你的朋友(对人类程序员也是如此)

- 可能会看到向更模块化或基于服务的架构转变

- LLM 有清晰的 API 边界可以在其中工作

- 同时保持一致的外部接口

- 比有大量相互依赖关系的巨大单体仓库好得多

- 这些对人类和 LLM 都很困难

- 不清楚一个地方的更改是否会影响代码库的另一部分

**现代架构优势**:

- 具有一致外部 API 的现代架构

- 可以更改内部实现

- 只要外部接口和测试仍然通过就没问题

### 9. 选择正确的技术栈

**经验案例:Ruby on Rails**

Tom 选择部分使用 Ruby on Rails 构建项目,主要因为他以前作为专业开发者时很熟悉。但他对 AI 在编写 Rails 代码时的性能感到震惊。

**为什么 Rails 效果好?**

- Rails 是一个有 20 年历史的框架

- 有大量完善的约定

- 许多 Rails 代码库看起来非常相似

- 有经验的 Rails 开发者很清楚特定功能应该放在哪里

- 知道实现某个结果的正确"Rails 方式"

- 这意味着在线有大量相当一致的高质量训练数据

**其他语言的情况**:

- 朋友在 Rust 或 Elixir 等语言上成功率较低

- 原因是在线训练数据不够多

- 但这可能很快就会改变

**选择建议**:优先选择有大量高质量训练数据的成熟框架。

### 10. 使用截图

**功能和应用**:

- 可以将截图复制粘贴到大多数编码代理中

- 非常有用的场景:

  - 展示 UI 实现中的 bug

  - 从其他网站引入设计灵感用于你的项目

### 11. 语音输入

**Aqua 的强大功能**:

- 可以直接对着电脑说话

- Aqua 将语音转录到正在使用的工具中

- 在 Windsurf 和 Claude Code 之间频繁切换都很方便

- 以 140 字/分钟的速度输入指令

- 大约是打字速度的两倍

**容错性优势**:

- AI 对轻微的语法和标点错误非常宽容

- 转录不完美也无关紧要

### 12. 频繁重构

**重构的时机和方法**:

- 当代码正常工作且测试已实施时

- 可以随意重构

- 测试会捕获任何回归

- 甚至可以要求 LLM 识别代码库中重复的部分

- 或可能适合重构的候选部分

**遵循专业实践**:

- 不要有数千行长的文件

- 保持文件小而模块化

- 对人类和 LLM 来说都更容易理解

### 13. 持续实验

**快速变化的领域**:

- 这个领域的最先进技术似乎每周都在变化

- 尝试每个新模型版本

- 看看哪个在不同场景中表现更好

**不同模型的优势**:

- 有些更擅长调试

- 有些更擅长长期规划

- 有些更擅长实现功能

- 有些更擅长重构

**当前模型对比(视频录制时)**:

- **Gemini**:最适合整个代码库索引和制定实施计划

- **Sonet 3.7**:目前实际实现代码更改的领先者

- **GPT-4.1**:刚试用几天,印象还不够深刻,问太多问题且实现经常出错,但下周会再试,情况肯定又会改变

## 可操作的要点总结

 1. **选择合适的工具**:初学者用 Replit/Lovable,有经验者用 Cursor/Windsurf/Claude Code

 2. **先计划后编码**:创建详细的 Markdown 计划,分步实施

 3. **虔诚使用 Git**:频繁提交,不怕 reset,保持代码库干净

 4. **编写高层次测试**:在每个功能完成前实施集成测试

 5. **复制粘贴错误消息**:这通常足以让 AI 修复问题

 6. **本地管理文档**:下载 API 文档到项目文件夹

 7. **模块化架构**:小文件、清晰边界、一致的外部 API

 8. **选择成熟框架**:优先使用有丰富训练数据的技术栈

 9. **多工具并行**:同时使用多个工具以提高效率

10. **频繁重构**:保持代码整洁、可维护

11. **持续实验**:尝试新模型,找到最适合不同任务的工具

12. **使用截图和语音**:充分利用多模态输入提高效率

## 结语

Vibe Coding 正在改变软件开发的方式。虽然 AI 还不能完美地一次性构建整个产品,但通过遵循专业软件工程实践——制定计划、使用版本控制、编写测试、保持模块化——你可以充分发挥 LLM 的潜力。

这是一个快速发展的领域,每周都有新的技巧和工具出现。保持好奇心,持续实验,分享你的发现。记住,最好的 Vibe Coding 实践本质上就是好的软件工程实践,只是现在有了 AI 这个强大的合作伙伴。

开始尝试,找到最适合你的工作流程,然后持续优化。未来几个月,随着模型能力的快速提升,这些最佳实践可能会继续演变,但核心原则——清晰的规划、系统的方法、持续的测试——将始终适用。
