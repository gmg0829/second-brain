## 引言

Andrej Karpathy 是 OpenAI 联合创始人、特斯拉前 AI 负责人，如今是 Eureka Labs 创始人。他以"让最复杂的技术听起来既平易近人又不可抗拒"而闻名。2025 年，他首次提出了 **vibe coding**（氛围编程）概念——一种用自然语言对话来编程的全新方式。2026 年初，他更进一步，公开表示"我从未感觉自己如此落后于作为一个程序员"。

这篇对话是关于这种落差感的深度解释，也是对正在形成的 **agentic engineering**（智能体工程）学科的系统性阐述。

---

## 第一部分：为什么 Karpathy 感到"落后"

### 1.1 一个清晰的分水岭：2025 年 12 月

Karpathy 回忆了他使用 AI 编程工具的演进过程：

> "我和其他人一样使用 agentic 工具，比如 Claude Code 和类似的产品，已经有一年左右了。它在处理代码块时表现很好，有时候会出错，你得去修改，有点帮助。然后到了 12 月，对我来说是一个清晰的分水岭——我正好在休假，有一些空闲时间。我开始注意到，随着最新的模型，代码块直接就能用，我不断要求更多，它就继续输出。我已经想不起上一次修改它是什么时候了。然后我就越来越信任这个系统，进入 vibe coding 模式，不停地产出各种 side project。"

这个转变的标志是**质变而非量变**：

- **之前**：AI 生成代码块，需要人类审查和修改，"有点帮助"
- **之后**：AI 生成代码块直接可用，不需要任何修改，"完全信任"
- 12 月的模型突破了某个阈值，使得**完整的端到端 vibe coding** 成为可能

Karpathy 强调，许多人去年对 AI 的认知还停留在 "ChatGPT adjacent"（类 ChatGPT 工具）的阶段，这是一个根本性的误判。他试图在 X（原 Twitter）上反复传达这一点：**到 12 月，一切都变了，尤其是 agentic 复杂工作流开始真正生效**。

### 1.2 双重感受：兴奋与不安

当被问及这种"落后感"是令人振奋还是令人不安时，Karpathy 的回答是：

> "两者兼有。"

他的 side projects 文件夹变得"极度充实"，充满了各种随机项目。这就是"落后感"的来源：**当你能够以 10 倍速度生产时，你的想法和野心也在膨胀，而膨胀的速度超过了你能跟上的速度**。

## 第二部分：Software 3.0——全新的计算范式

### 2.1 软件发展的三次革命

Karpathy 提出了一个清晰的三段式框架来理解软件演变：

| 时代 | 范式 | 核心工作 |
|------|------|---------|
| **Software 1.0** | 显式规则 | 人类编写明确的代码规则，程序员敲键盘写代码 |
| **Software 2.0** | 学习权重 | 程序员变成"数据整理者"——创建数据集、定义目标函数、设计神经网络架构 |
| **Software 3.0** ⭐ | 上下文工程 | 编程变成写提示词，上下文窗口是操控 LLM 这台解释器的杠杆 |

Karpathy 用了一个形象的比喻：

> "上下文窗口就是你的杠杆，LLM 就是解释器，它解读你的上下文，在数字信息空间中执行计算。"

### 2.2 第一个活生生的例子：OpenClaw 安装

Karpathy 描述了传统软件安装和 Software 3.0 方式的根本区别：

**传统方式（Software 1.0 思维）**：
- 下载一个 bash shell 脚本
- 脚本需要适配多种平台、多种计算机环境
- Shell 脚本膨胀得极其复杂，到处是条件判断和平台适配代码

**Software 3.0 方式**：
- 安装指南就是"复制粘贴给 agent 的一段文本"
- Agent 有自己的智能，它会：
  1. 理解指令
  2. 检查你的环境
  3. 执行智能操作
  4. 在循环中调试
- 你不需要精确描述"在 Ubuntu 22.04 上执行第 3 行、在 macOS Sonoma 上跳过第 5 行"

Karpathy 的总结振聋发聩：

> "所以这就是我现在看待编程的方式——**什么是我应该复制粘贴给 agent 的那段文本？** 这就是新的编程范式。"

### 2.3 第二个震撼案例：Menu Gen

Karpathy 讲述了他自己构建 **Menu Gen** 的故事。这个项目的想法很简单：
> 去餐厅，服务员给你一份没有图片的菜单。你大概有 30%-50% 的菜品完全不知道是什么。Menu Gen 的功能是：拍照 → OCR 识别所有菜品名 → 用图像生成器为每个菜品生成示意图片 → 渲染出一份带图的菜单。

他用 vibe coding 方式构建了这个 app：
- 运行在 Vercel 上
- 调用图像生成 API
- 处理 OCR
- 渲染前端

**然而，真正的 Software 3.0 版本让他彻底震惊**：

> "Gemini + Nano Banana 的方案只需要：拍照 → 给 Gemini → 说'用 Nano Banana 把这些菜叠加到菜单图片上' → 直接输出一张完美渲染的菜单照片——就是用户拍摄的那张照片，但菜已经图像化地渲染到像素上了。"

他的整个 Menu Gen app 在旧范式中是"多余的存在"。Software 3.0 方式是：**输入是照片，输出是照片，中间没有"app"**。神经网络的端到端处理让所有中间层都变得不必要。

### 2.4 新范式的真正含义

Karpathy 反复强调一个关键点：

> "不要把 Software 3.0 看作是对现有事物的加速，要把它看作是完全前所未有的新事物的出现。"

他举了一个更极端的例子来说明这种范式转变的深远性：

> "你完全可以想象一个完全神经化的计算机——输入原始视频或音频，经过神经网络处理，用 diffusion 渲染出一个针对当前情境独特生成的 UI。这不是把现有东西做得更快，这是全新的东西。"

他还提到了计算历史上一个鲜为人知的趣闻：

> "在 50 年代和 60 年代，人们其实不确定计算机应该像计算器还是像神经网络。最后我们走了计算器的路，建成了经典计算，然后神经网络目前运行在现有计算机的虚拟化环境中。但我认为未来会逆转——神经网络会成为主机进程，CPU 会变成协处理器。"

## 第三部分：可验证性——理解 AI 能力参差不齐的关键

### 3.1 可验证性假说

Karpathy 深入阐述了他对 AI 能力分布的理解，提出了一个核心框架：

> **传统计算机**：能自动化"能用代码精确指定"的工作
> **LLM**：能自动化"能验证结果"的工作

背后的原因是训练范式：前沿实验室训练 LLM 时使用的是大型**强化学习环境（RL environments）**，模型根据**验证奖励（verification rewards）** 来进步。这直接导致了 LLM 的一个核心特征——**能力高度参差不齐（Jagged Intelligence）**。

### 3.2 能力的参差性：令人困惑的矛盾

Karpathy 用一个令人难忘的例子来说明这种矛盾：

> "最先进的 Opus 4.7 模型能同时重构一个 10 万行的代码库，发现零日漏洞——但会建议你步行去 50 米外的洗车场，因为'太近了，走路吧'。这完全疯了。"

**Strawberry 问题**：模型能处理复杂的代码重构，却会在"strawberry 这个词里有几个 r"这种简单问题上一再出错。这不是模型"不够聪明"，而是它在某些能力上被强化训练（进入了 RL 的"电路"），在其他能力上则完全没有训练（处于数据分布之外）。

Karpathy 进一步用**国际象棋**的例子说明数据分布的力量：

> "从 GPT 3.5 到 GPT 4，人们注意到国际象棋能力提升了很多。很多人以为这只是能力渐进提升。但实际上——我看到过这个公开信息——大量象棋数据被加入到了预训练集中。因为这些数据在预训练集中，模型在国际象棋上的表现远超默认水平。**是有人在 OpenAI 专门决定加入这些数据的**。"

这揭示了一个重要真相：**LLM 的能力在很大程度上取决于实验室选择把什么数据加入训练集，以及 RL 环境关注哪些验证目标**。用户在一定程度上"受制于"实验室的决策——你在这个应用的"RL 电路"内就飞速前进，在这个应用的"RL 电路"外就困难重重。

### 3.3 幽灵隐喻

Karpathy 用一个深刻的类比来描述 LLM 的本质：

> "LLM 不是动物。动物有内在动机，有好奇心，有主动性，有乐趣。LLM 是**被召唤的幽灵**——它们是由数据和奖励函数塑造的统计实体。"

"幽灵"的特点：

- **锯齿状（Jagged）**：能力高度不均匀，某些领域极强，其他领域极弱
- **统计性（Statistical）**：基于概率分布运作，而非确定性逻辑
- **被召唤（Summoned）**：需要被引导，需要清晰的上下文来激活正确的"电路"
- **无内在动机**：不会因为"好奇"而主动探索

这意味着你不能简单地期待 LLM "变聪明"，你需要理解它在哪个"电路"里，然后针对性地设计和调试。

## 第四部分：Vibe Coding vs Agentic Engineering

### 4.1 两个概念的对比

| | **Vibe Coding** | **Agentic Engineering** |
|---|---|---|
| **目标** | 降低编程门槛，让任何人都能创作 | 在加速的同时保持专业软件的质量标准 |
| **核心特征** | 非正式、探索性、允许错误 | 系统性、高标准、不允许安全漏洞 |
| **本质** | 提高编程的"地板" | 拉高编程的"天花板" |
| **风险** | 可能引入安全漏洞和质量问题 | 如何在速度和质量之间取得平衡？ |
| **适用者** | 任何人 | 专业软件工程师 |

Karpathy 明确表示：

> "Vibe coding 是关于把编程的地板抬高，让每个人都能做任何事，这很棒。但 agentic engineering 是关于保持专业软件的 bar——你不允许因为 vibe coding 而引入安全漏洞。你仍然为软件负责，只是能更快。那你怎么才能做到这一点？"

### 4.2 协调的难题

Karpathy 描绘了 agentic engineering 的核心挑战：

> "agentic engineering 所面对的实体是**锯齿状的**——它们有点像个寓言，有点随机，但极其强大。如何协调它们，让它们在不牺牲质量标准的前提下加快速度——这就是 agentic engineering 的领域。"

他观察到，有天赋的 agentic engineer 的能力提升远超 10 倍：

> "过去人们谈论 10x 工程师，我认为 agentic engineering 的放大效果远不止 10 倍。"

### 4.3 实践中的问题：Agent 仍然会犯"荒谬"的错误

Karpathy 分享了一个 Menu Gen 开发中的真实 bug：

> "Menu Gen 使用 Google 账号登录，但购买 Credits 用的是 Stripe。两者都有邮箱地址。我的 agent 实际上尝试用 Stripe 的邮箱地址来匹配 Google 账号的邮箱地址——它假设同一个人的两个账号用同一个邮箱。完全没有持久性用户 ID 的概念。"

这是 agent 做出的"荒谬"决策——因为它不理解为什么不同系统会用不同的邮箱，也不知道应该用唯一用户 ID 来关联。用户必须事先设计好系统的正确架构，然后 agent 才能在正确的框架内工作。

## 第五部分：人类仍然不可替代什么？

### 5.1 品味、判断力与监督

Karpathy 明确表示，即使 AI 能处理越来越多细节，**人类在顶层仍然不可替代**：

- **品味（Taste）**：什么是美的、什么是合适的
- **判断力（Judgment）**：在多个选项中做出正确选择
- **监督（Oversight）**：确保整体方向正确

他以自己为例：

> "即使现在，我用的大多数框架和库，它们的文档仍然是为人写的。我最烦的是：为什么文档还在告诉我'你应该做什么'？我不想做那些事——我只想知道'应该把什么复制粘贴给 agent'。"

这是基础设施尚未面向 agent 原生设计的证据。

### 5.2 API 细节与高层理解

Karpathy 还提到了一个有趣的现象：他已经忘记了 PyTorch/NumPy 很多 API 的细节（比如 `keep_dims` vs `keep_dim`，`axis` vs `dim`，`reshape` vs `permute` vs `transpose`），但这没关系，因为：

> "这些是 agent 可以帮你处理的细节。你不需要记住它们——agent 有完美的记忆力。但你仍然需要知道存在某个 underlying tensor、某个 view 概念，知道可以在同一个 storage 上 manipulate view——否则你可能会低效地复制内存。"

换句话说：**细节被外包给了 agent，但高层理解仍然必须保留在人类脑中**。

### 5.3 与 Agent 共同设计规格

Karpathy 提出了一个关键的工作流：

> "我不喜欢 plan mode（计划模式）。但它本质上是一个与 agent 共同设计详细规格的过程——然后让 agent 编写这些规格文档。你负责顶层分类和监督。"

更一般的模式是：
1. 你设计顶层规格（spec）——唯一用户 ID 是什么？核心数据结构是什么？
2. Agent 填充所有细节
3. 你负责验证和监督

这就是 **Spec-Driven Development** 的核心：人做设计，agent 做实现。

## 第六部分：对创始人的建议

### 6.1 可验证性强的领域仍然有机会

Karpathy 的建议基于他的可验证性框架：

> "如果你处在一个可验证的环境中，你可以创建自己的 RL 环境，或者创建足够的 examples，你就能受益于微调。如果你在一个可验证的领域，**技术本身是有效的**——你只需要正确地 pull the lever。"

他暗示，某些领域目前没有被前沿实验室的 RL 充分覆盖，但仍然具有极高的经济价值——这些是创始人的机会。

### 6.2 招聘 Agentic Engineer 的新方式

Karpathy 直言不讳地批评了传统的编程面试：

> "如果你的面试仍然是白板解题，你还没有重新构建你的 agentic engineer 招聘流程。招聘 agentic engineer 应该：给他们一个大项目——比如'用 agent 搭建一个 Twitter clone'——让它质量足够高、安全性足够好，然后用 10 个 agent 模拟活动，让另外 5 个 agent 用各种方式攻击它——看看它能否抵御。"

这才是真正测试 agentic engineer 能力的方式。

## 第七部分：关于教育和学习

### 7.1 一句让他每次都心头一震的话

Karpathy 透露了他最近看到的最震撼的一句话：

> **"你可以外包你的思考，但你永远无法外包你的理解。"**

他接着阐述：

> "即使 AI 在处理信息，我仍然是系统的一部分。我仍然需要知道我们试图构建什么、为什么值得做。我需要知道如何指导我的 agent。如果我不理解某个领域，我就无法有效地指导 agent。我仍然是 bottleneck。"

### 7.2 LLM 作为知识管理工具

Karpathy 分享了他个人的工作流：

> "当我阅读文章时，我会用 LLM 构建一个 wiki。当我处理信息时，我总是喜欢看到不同的投影——这总让我获得新的洞察。我用 prompts 做合成数据生成，生成对固定数据的新视角。"

这指向了一个未来图景：**个人知识管理系统 + AI 增强 = 持续学习的新方式**。工具增强了理解，但理解本身仍然是人类的责任。

### 7.3 什么仍然值得深入学习

Karpathy 对"当智能变得廉价时，什么还值得学习"这个问题的回答是：

1. **理解本身**——不能外包
2. **如何成为好的"导演"**——知道要什么、为什么
3. **高层架构思维**——即使细节可以外包，顶层设计不能外包

## 第八部分：面向 Agent 原生的未来

### 8.1 Agents Everywhere

Karpathy 描绘了一个 Agents 无处不在的未来：

> "我们正在走向一个每个个人和每个组织都有 agent 代表的世界。我的 agent 会和你的 agent 交流，来敲定我们会议的细节等等。"

这个未来需要：
- **面向 agent 描述的基础设施**（而不是面向人）
- **Agent-native 的数据结构**（Agent 能轻松读取和操作的格式）
- **"首先描述给 agent"的文档哲学**

### 8.2 传感与执行

Karpathy 提出了一个优雅的框架：

> "计算 workloads 将被分解为**传感（sensors）** 和**执行器（actuators）**——感知世界的方式和作用于世界的方式。重点是：如何让系统首先面向 agent 描述，然后让自动化围绕它展开。"

他认为，infra 层需要从根本上重新设计，让 agent 能够理解和操作系统，而不是让人类成为中间层。

## 关键概念解释

### Software 3.0

一种全新的计算范式，其中编程从"写代码"转变为"写提示词"，上下文窗口成为操控 LLM 解释器的核心杠杆。

### Vibe Coding

一种用自然语言对话进行编程的方式，任何人都可以参与，但可能引入安全和质量风险。核心是降低编程的门槛。

### Agentic Engineering

在利用 AI 加速编程的同时保持专业软件质量标准的工程学科。需要协调"锯齿状的"agent 实体，在不牺牲质量的前提下提速。

### 可验证性（Verifiability）

LLM 能够自动化"能验证结果"的工作。因为 RL 环境提供验证奖励，所以 LLM 在可验证领域（代码、数学）表现出色，在不可验证领域参差不齐。

### 锯齿状的智能（Jagged Intelligence）

LLM 能力的非均匀分布状态——某些领域极强（如代码重构），某些领域极弱（如常识推理）。这是由训练数据和 RL 目标函数决定的。

### 幽灵隐喻

Karpathy 将 LLM 描述为"被召唤的幽灵"——它们是由数据和奖励函数塑造的统计实体，没有内在动机、好奇心或主动性，需要人类引导才能正确运作。
