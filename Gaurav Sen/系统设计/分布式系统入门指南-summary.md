# System Design Primer: How to start with distributed systems?

## 内容概要

视频使用披萨餐厅的经营比喻来解释分布式系统的基础概念。起初一家披萨店只有一名厨师，当订单过多厨师忙不过来时，第一反应是让厨师更努力工作（给更多钱、优化流程），这对应技术术语中的垂直扩展（Vertical Scaling）——用相同资源榨取更多产出。进一步优化可以在非高峰时段预先准备工作，比如提前制作面团，这样高峰时段厨师不必临时制作基础原料，直接专注于烹饪。

然而一名厨师是单一故障点——一旦他生病请假，整天的生意都没法做。对应技术方案是设置备用厨师（Backup Servers / Master-Slave Architecture）。当业务持续增长，备用厨师变成全职，同时招聘更多厨师，这对应水平扩展（Horizontal Scaling）——购买更多相同规格的机器来承担更多工作。

接下来将厨师按专长分组：擅长做披萨的厨师负责披萨订单，擅长做蒜香面包的厨师负责蒜香面包。这对应微服务架构（Microservices）——按业务能力划分团队，每个团队职责明确且可独立扩展。一个团队内部也可以按不同比例扩展，比如披萨团队需要 7 人，蒜香面包团队只需要 3 人，因为订单量不同。

当披萨店面临停电或执照吊销等全局性故障时，唯一的店就意味着彻底无法营业。对应分布式系统（Distributed Systems）——在不同地理位置开设分店，即使一家店完全不可用，其他店依然能提供服务。大型互联网系统如 Facebook 需要在全球各地部署服务器（边缘服务器），既提高容错能力，也降低用户访问延迟。

多店铺运营带来路由问题：顾客下单后应该由哪家店处理？不能让顾客自己做这个决定。需要一个中央路由机制，根据每家店的当前负载智能选择——比如哪家店当前等待时间更短就优先路由到那家。这就是负载均衡器（Load Balancer）的概念，它收集各服务节点的实时状态，做出最优分配决策。

披萨制作和配送两件事本质上是独立的：配送员只需要把东西尽快送到顾客手中，不在乎是披萨还是汉堡；披萨店也不在乎是配送员取货还是顾客自取。这就是解耦（Decoupling）——将关注点分离，让各系统可以独立演化和优化。当某个设备出现故障（如烤箱坏了或配送员摩托车坏了），需要日志（Logging）记录每个事件的发生时间和后续事件链，以及指标（Metrics）来聚合分析这些事件，发现问题根源。

系统的最终要求是扩展性（Extensibility）——配送员今天送披萨，明天可能送汉堡，系统设计应该支持这种变化而无需重写代码。Amazon 从最初只送包裹发展到现在送各种商品，正是因为从一开始就将系统设计为可扩展的。总结来说，将真实商业场景映射到技术方案，就形成了高层系统设计（High Level Design）；而低层系统设计（Low Level Design）则涉及具体的类设计、函数签名、代码实现等，更贴近工程师的日常工作。

## 核心观点

- 垂直扩展（让单机更强）和水平扩展（增加更多机器）是应对负载增长的两种基本策略
- 单一故障点（Single Point of Failure）是系统设计必须规避的核心风险，通过备份和冗余实现容错
- 微服务架构的本质是按业务能力划分团队，每个服务职责单一、可独立扩展
- 分布式系统的核心价值不仅是扩展能力，更是容错——多地部署避免单点故障影响全局
- 负载均衡器通过收集实时状态数据（等待时间、负载率），做出智能路由决策
- 解耦是将无关的关注点分离，使各部分可以独立演进，不互相影响
- 可扩展性要求系统在不需要重写的情况下支持新业务类型的加入

## 关键术语

- **Vertical Scaling（垂直扩展）**: 通过升级单机硬件（CPU、内存、磁盘）来提升单机处理能力
- **Horizontal Scaling（水平扩展）**: 通过增加更多机器实例来提升整体系统处理能力
- **Backup Servers / Master-Slave**: 主从架构，主节点故障时从节点接管服务
- **Microservices（微服务架构）**: 将大型应用拆分为多个独立部署、独立扩展的服务，每个服务专注特定业务功能
- **Distributed Systems（分布式系统）**: 跨多个地理节点部署的系统，提高容错性和降低访问延迟
- **Load Balancer（负载均衡器）**: 收集各节点状态，将请求智能路由到最适合处理的服务节点
- **Decoupling（解耦）**: 分离关注点，使系统各部分可独立演化和测试
- **Logging（日志）**: 记录系统中事件的发生时间和序列，用于问题追踪
- **Metrics（指标）**: 聚合后的数据指标，用于分析系统运行状况和性能
- **Extensibility（扩展性）**: 系统支持新增功能或业务类型而无需大幅修改现有代码的能力
- **High Level Design（高层系统设计）**: 关注系统架构、服务交互、部署策略等宏观设计
- **Low Level Design（低层系统设计）**: 关注具体的类设计、函数签名、代码实现等微观设计
