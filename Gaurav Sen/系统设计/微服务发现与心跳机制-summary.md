# 服务发现与心跳机制：微服务可用性的两大基石

## 一、开场：一个关于可靠性的真实故事

视频以一段戏剧化的对话开场：

> **工程师A**：我们的数据管道太慢了，需要更快地处理数据！
> **工程师B**：那我们加 NoSQL 数据库吧，Cassandra 适合这个规模。
> **工程师A**：成本呢？
> **工程师B**：大约 100 万美元。
> **工程师A**：分库分表呢？
> **工程师B**：迁移大概需要几周。
> **工程师A**：那先增加 50% 的服务器吧。
> **工程师C**（走过来）：我刚跑了健康检查，发现只有 50% 的服务器在线……
> **工程师A**（被提拔了）
> **工程师B**（被解雇了）

**核心启示**：服务端工程师的大部分工作不是"让系统更高效"，而是**"让系统一直可用"**。当系统宕机时，用户会流失、收入会下降——可用性直接影响业务生死。

## 二、单向心跳机制（One-Way Heartbeat）

### 基本工作原理

```
Health Service（健康服务）
    ↓ 每5秒发送一次"Are You Alive?"
S1 Server ──── "Yes, I'm alive." ────→ Health Service ✓
S2 Server ──── "Yes, I'm alive." ────→ Health Service ✓
S3 Server ──── "No response" ────→ Health Service ✗ → 标记为 CRITICAL
```

### 故障检测流程

1. **正常状态**：Health Service 每 5 秒轮询所有服务节点，所有节点正常响应，系统正常运行。
2. **第一次无响应**：如果 S1 对 Health Service 的探活请求没有响应，S1 被标记为 **CRITICAL（危险）**。
3. **第二次无响应**：如果连续两次（累计约 10 秒）都没有响应，则确认 S1 已死亡（Dead）。
4. **自动恢复**：
   - Health Service 通知负载均衡器（Load Balancer）：S1 已下线，将其从路由池移除。
   - 自动触发服务重启或故障转移：将服务迁移到新节点 S4 重新部署。

### 为什么要等待"两次无响应"？

避免误判——网络抖动、一次偶发的丢包不应触发完整的故障恢复流程。等待连续两次无响应可以有效过滤噪声。

## 三、双向心跳机制（Two-Way Heartbeat）：防止僵尸服务

### 单向心跳的隐藏缺陷

单向心跳有一个致命的盲区：**服务器可能处于"僵尸状态"（Zombie）**。

**僵尸进程问题**：
- 服务器 S4 回答 Health Service 的"Are You Alive?" —— 因为操作系统层面它还"活着"（硬件正常、进程还在）。
- 但应用层（如 HTTP 服务）已经完全卡死，无法处理任何请求。
- 同时，S4 可能还在运行定时任务（cron jobs），向其他服务发送请求，但这些请求携带的是**过期数据（Stale Data）**，可能正在破坏其他服务的内部状态。

### 双向心跳的解决方案

```
Health Service <──── heartbeat (每5秒) ──── S4（主动上报）
Health Service ──── heartbeat (每5秒) ────→ S4（被动确认）
```

**双向心跳的本质**：
- 不仅 Health Service 询问服务是否存活，**服务本身也要主动上报自己的存活状态**。
- 如果 S4 被 Health Service 标记为死亡，S4 会收到通知，然后**主动自我终止（Kill Itself）**，防止僵尸服务继续影响其他节点。
- 任何一方心跳中断，即可判断对方已不健康。

### 关键洞察

> 双向心跳不能 100% 解决僵尸进程问题，但能**大幅缓解**——因为任何一方发现异常都可以触发隔离动作。

## 四、服务发现（Service Discovery）：动态注册与路由更新

### 服务发现的必要性

当 Profile Service（用户信息服务）在三台机器 S1、S2、S3 上部署时，它需要告诉两件事：

1. **负载均衡器**：哪些 IP + Port 上有我的服务实例？
2. **其他服务**：如何找到 Profile Service？

### 服务注册流程

```
Profile Service（S1, S2, S3）注册
        │
        ↓
[Load Balancer Snapshot（快照）]
  IP: 10.0.0.1  Port: 8080  ✓
  IP: 10.0.0.2  Port: 8080  ✓
  IP: 10.0.0.3  Port: 8080  ✓
        │
        ↓
通知所有服务：Profile Service 的实例列表已更新
```

### 快照机制（Snapshot）

- 负载均衡器存储当前所有可用服务实例的完整快照（IP、Port、协议类型等）。
- 快照是有版本号的，每次变更（新增实例、下线实例）都会产生新版本。
- 快照持久化到数据库，支持故障恢复后快速重建路由表。

### 缓存快照以降低开销

如果每次查询服务地址都要访问负载均衡器，网络开销很大。实际系统中，**各服务通常在本地缓存一份快照**，并通过以下方式保持更新：
- 定时从负载均衡器拉取最新快照（Pull 模式）
- 或等待变更通知后更新本地缓存（Push 模式，如 UDP 广播或 gRPC 流式推送）

## 五、Health Service 与 Service Discovery 的协作

```
[Profile Service] 上线
        │
        ├──→ [Load Balancer] 更新 Snapshot（加入 S1, S2, S3）
        │
        └──→ [Health Service] 检测到 diff（快照变化）
                    │
                    └──→ 主动与 S1, S2, S3 建立 HTTP 连接
                        每5秒轮询"Are You Alive?"
                        发现异常 → 通知 Load Balancer 更新快照
```

**Health Service 的双重职责**：
1. **变更检测**：监听快照变化，当新服务注册时，主动建立与该服务的连接，开始心跳检测。
2. **持续监控**：确保所有在线服务实例的健康状态，一旦发现故障立即通知负载均衡器更新路由。

## 六、总结：服务发现与健康检查的核心要点

| 机制 | 解决的问题 | 关键设计 |
|---|---|---|
| 单向心跳 | 节点是否存活 | 轮询间隔、连续两次无响应才判定死亡 |
| 双向心跳 | 僵尸进程、过期数据 | 服务主动上报，应用层+系统层双重确认 |
| 服务注册 | 动态扩缩容时的路由更新 | 快照版本号、持久化存储 |
| Health Service | 监控 + 通知 | 与负载均衡器联动，触发故障转移 |

**工程实践建议**：

1. **心跳间隔**：通常设为 5~30 秒。太短容易误判网络抖动，太长则故障发现延迟大。
2. **故障阈值**：至少连续 2~3 次无响应才判定死亡，减少误触发。
3. **主动上报 + 被动探测结合**：服务本身主动上报自身状态（双向心跳），Health Service 作为独立第三方做被动探测。
4. **快照缓存**：各服务本地缓存服务实例列表，减少对中心组件（负载均衡器）的依赖，提高系统整体的抗压能力。

> 服务发现和健康检查共同构成了微服务可用性的"双保险"——一个负责"谁来处理请求"，一个负责"哪些处理者还活着"，二者缺一不可。
