# System Design: Online Judge for coding contests

## 内容概要

在线评测系统（Online Judge）是竞技编程和面试准备平台的核心基础设施，典型代表包括 LeetCode 和 Codeforces。本视频深入探讨了远程代码执行引擎的系统设计，从最简单的直连方案出发，逐步演进到能够支撑数千用户同时提交的高可用架构。

视频首先提出了最朴素的解决方案：用户上传代码文件，服务器直接执行该文件，传入测试用例输入，比对输出是否与预期结果一致。这种方案在低并发场景下工作良好，但面临严峻的挑战——当一场比赛中有数千用户同时提交代码时，同步处理会迅速导致服务器过载。限流虽然能保护系统，但对用户公平性造成严重损害，尤其在竞赛场景中让精心准备的参赛者仅仅因为系统无法承载而被淘汰是完全不可接受的。

为了解决这个问题，视频引入了消息队列作为异步处理的核心组件。用户的代码上传后不再同步执行，而是立即得到上传确认，同时一个包含代码文件URL等关键信息的事件被发布到消息队列。这种异步化处理确保用户体验的流畅性——用户知道代码已成功接收，而服务器可以按照自身的处理能力逐一消化待执行的提交。代码文件本身通常存储在分布式文件系统（如S3）中，而非直接存放在执行服务器上。

安全隔离是远程代码执行系统最关键的设计要点之一。视频详细讨论了容器化技术来防止恶意代码危害宿主服务器。通过Docker或Kubernetes等容器技术，每份提交的代码都在独立的虚拟环境中执行，即使代码包含 rm -rf 这样的危险命令，其破坏范围也被限制在容器内部，最多导致容器崩溃而不会影响主机或其他用户的代码。相较于完整的虚拟机，容器更加轻量，创建和销毁的开销小得多，更适合高频率的代码执行场景。

最后，视频总结了远程代码执行引擎的核心组件：任务调度器（Job Scheduler）用于控制并发量防止服务过载，以及容器化执行环境用于提供安全隔离。视频强调，在面试中讨论这类系统时，应该直击核心问题，不要在身份认证、网关等周边服务上绕圈子——远程代码执行引擎的本质就是"如何安全地隔离执行用户代码"。

## 核心观点

- 同步处理用户代码提交在并发场景下会导致服务器过载，限流虽然可行但严重损害用户体验和竞赛公平性
- 消息队列是实现异步处理的关键组件，使用户提交与实际执行解耦，服务器按能力消费队列事件
- 分布式文件系统（如S3）适合存储用户上传的代码文件，与执行服务分离便于扩展和管理
- 虚拟化和容器技术提供了代码执行的安全隔离，限制恶意代码对系统其他部分的破坏
- 容器比完整虚拟机更轻量，更适合代码评测这种高频创建销毁场景
- 远程代码执行系统的核心问题只有两个：任务调度（防止过载）和容器化（安全隔离）

## 关键术语

- **远程代码执行引擎（Remote Code Execution Engine）**：接收用户提交的代码、在隔离环境中执行、并根据预设测试用例验证输出正确性的系统
- **在线评测系统（Online Judge）**：提供编程题目、接收代码提交、自动评判正误的竞技编程平台
- **异步处理（Asynchronous Processing）**：用户提交后立即返回确认，实际执行稍后进行的处理模式
- **消息队列（Message Queue）**：临时存储待处理事件的队列，生产者发布事件，消费者按序处理
- **容器化（Containerization）**：使用Docker等工具创建轻量级隔离执行环境的技术，比虚拟机更高效
- **任务调度器（Job Scheduler）**：控制并发任务数量、防止系统过载的调度组件
- **测试用例（Test Case）**：用于验证代码正确性的输入输出数据对

## 关键语录

> "远程代码执行引擎的核心问题只有两个：任务调度器和容器化。任务调度防止过载，容器化提供安全隔离——这就是面试中你需要讲清楚的全部。"
